What is a Database?

Introduction

A database is an organized collection of data stored so that it can be efficiently retrieved, updated, and managed. Before we can compare database types or design one, we need a shared vocabulary: data versus information, records, fields, and tables, and the software layer — the database management system (DBMS) — that sits between users and the stored data. This topic builds that foundation.

This matters for everything that follows in COP4708. Later in the module you will distinguish relational, NoSQL, and hierarchical models and choose the right one for a given scenario. Those decisions only make sense once you can say precisely what a database is, what problems it solves that a spreadsheet does not, and what a DBMS actually does for you (storage, querying, concurrent access, security, and integrity).

As you watch, keep a running glossary. Note how each speaker defines a database, where tables, rows (records), and columns (fields) appear, and when the discussion shifts from the data itself to the DBMS that manages it. Also notice any mention of selection criteria — scalability, structure, consistency — since those terms return later in the module.

Relational Databases

Introduction

A relational database organizes information into tables made up of rows (records) and columns (fields). Each table describes one kind of thing — customers, orders, patients, courses — and a defined schema states what columns exist, what type of data each holds, and what rules the data must follow. Tables are connected to one another through keys: a primary key uniquely identifies each row in a table, and a foreign key in one table points to the primary key of another, creating a relationship the database itself can enforce.

This structure matters for the rest of the course because it is the baseline against which every other database model is compared. When we later look at NoSQL and hierarchical systems, the questions we ask — how rigid is the schema, how are relationships represented, how easily can we query across data sets, how well is data integrity protected — are questions that come directly from the relational model. SQL, the language used to define and query relational data, is also the common point of reference for discussing query capability.

As you watch, keep a running vocabulary list: table, row, column, schema, primary key, foreign key, constraint, join, normalization. Pay attention to why designers split data across multiple tables instead of storing everything in one large table, and notice how the videos illustrate relationships (one-to-one, one-to-many, many-to-many) and what a foreign key constraint prevents from happening.

NoSQL Databases

Introduction

NoSQL databases emerged as an alternative to the relational model for situations where rigid table structures, fixed schemas, and single-server scaling become limitations. Instead of organizing everything into rows and columns linked by keys, NoSQL systems store data in formats that more closely match how applications actually use it: documents, key-value pairs, wide columns, or graphs. The name is usually read as "not only SQL" rather than a rejection of SQL, because most organizations run both kinds of systems side by side.

In this course, NoSQL matters because it gives you a second point of comparison. Once you can describe how a relational database enforces structure and integrity, you can evaluate what a NoSQL system gains (flexible schema, horizontal scaling across many commodity servers, high write throughput) and what it gives up (standardized querying, multi-table joins, strict consistency guarantees). That trade-off analysis is the heart of choosing a database for a real application.

As you watch the videos below, keep a running comparison table in your notes. Look for: the four main data models and what kind of data each suits; what "schemaless" or "flexible schema" actually means in practice; the difference between scaling up and scaling out; and the specific workloads — large-scale web apps, real-time analytics, content and session storage, social graphs — where NoSQL tends to win. Equally important, note where the videos acknowledge limitations, because no single database type is correct for every scenario.

Hierarchical Databases

Introduction

Hierarchical databases organize information as a tree: a single root record branches into child records, and each child has exactly one parent. This structure was the dominant approach in early commercial database systems such as IBM's IMS, and it still shapes how we think about nested data today — think of file systems, organizational charts, or XML and JSON documents. Because relationships are built directly into the storage structure through parent-child links, navigating a hierarchical database means following those links from the root downward rather than writing a declarative query.

In this course, hierarchical databases matter for two reasons. First, they give you historical context: understanding what came before the relational model makes it much clearer why tables, keys, and SQL were such an important advance. Second, they sharpen your ability to compare models — hierarchical databases are fast and predictable for queries that follow the tree, but awkward or impossible for many-to-many relationships and for questions the designer did not anticipate.

As you watch, look for three things: how the tree structure and parent-child rule are defined, how data access and navigation differ from relational querying, and where each model's strengths and limitations show up. Note that the third video shifts from data models to B-trees, an internal tree structure used inside modern database engines — keep that distinction clear in your notes, since a tree-shaped index is not the same thing as a hierarchical data model.

Comparing Database Types

Introduction

Up to this point you have met relational, NoSQL, and hierarchical databases one at a time. This topic places them side by side so you can see how their structures, schemas, query languages, scaling behavior, and consistency guarantees differ — and, more importantly, why those differences matter when someone has to pick one for a real system.

There is no "best" database. A rigid schema that feels restrictive in one project is exactly what protects financial records in another; a flexible document store that speeds up a startup's prototype can quietly allow inconsistent data later. The goal here is to build a mental checklist of selection criteria: What does the data look like? How will it be queried? How much will it grow? How costly is an inconsistent read?

As you watch the two videos below, keep a comparison table in your notes with columns for structure, schema flexibility, query power, scalability, and integrity. Note the vocabulary each speaker uses (normalization, joins, ACID, horizontal versus vertical scaling, eventual consistency) and jot down the example use cases they mention — you will be asked to justify database choices for similar scenarios later in this module.

Real-World Applications of Databases

Introduction

Almost every digital service you used today was backed by a database. When you browse a product catalog, check a bank balance, refill a prescription, submit an assignment, or scroll a social feed, software is reading from and writing to a data store that someone designed on purpose. This topic looks at that connection between database theory and the systems people actually rely on: e-commerce and retail, healthcare records, banking and financial services, social media and content platforms, education and learning management systems, government and public services, and transportation and logistics.

The reason this matters in COP4708 is that different industries place very different demands on their data. A bank cannot tolerate a transfer that debits one account without crediting another, so it leans on strict transactional guarantees. A social platform serves enormous volumes of reads and can often accept slightly stale data in exchange for speed and scale. A hospital must keep records accurate, auditable, and available. Those pressures — correctness, scale, flexibility, and reporting needs — are what push designers toward relational, NoSQL, or other models.

The three videos below come from ByteByteGo, a channel focused on system design. Rather than touring industries one by one, they give you the vocabulary that explains why industries choose what they choose: transactional guarantees, core architectural building blocks, and the pipelines that move data from operational systems into analytics. As you watch, keep asking yourself which industry from the subtopic list would care most about each idea, and why.
