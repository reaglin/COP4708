Introduction

NoSQL databases emerged as an alternative to the relational model for situations where rigid table structures, fixed schemas, and single-server scaling become limitations. Instead of organizing everything into rows and columns linked by keys, NoSQL systems store data in formats that more closely match how applications actually use it: documents, key-value pairs, wide columns, or graphs. The name is usually read as "not only SQL" rather than a rejection of SQL, because most organizations run both kinds of systems side by side.

In this course, NoSQL matters because it gives you a second point of comparison. Once you can describe how a relational database enforces structure and integrity, you can evaluate what a NoSQL system gains (flexible schema, horizontal scaling across many commodity servers, high write throughput) and what it gives up (standardized querying, multi-table joins, strict consistency guarantees). That trade-off analysis is the heart of choosing a database for a real application.

As you watch the videos below, keep a running comparison table in your notes. Look for: the four main data models and what kind of data each suits; what "schemaless" or "flexible schema" actually means in practice; the difference between scaling up and scaling out; and the specific workloads — large-scale web apps, real-time analytics, content and session storage, social graphs — where NoSQL tends to win. Equally important, note where the videos acknowledge limitations, because no single database type is correct for every scenario.
