Lecture 12-1 - Database Redesign

Video Lecture

Denormalization is the process of intentionally introducing redundancy into a database design. It's the opposite of normalization, which aims to reduce redundancy. While normalization is generally preferred for data integrity, denormalization can sometimes improve query performance. It's a trade-off: you gain speed but potentially sacrifice some data consistency.

Here are some examples and the reasoning behind denormalization:

1. Storing Calculated Values:

  • Scenario: You have a table of products with price and quantity columns. You frequently need to calculate the total_price for each product.
  • Normalization: You would typically calculate total_price in your queries.
  • Denormalization: You could add a total_price column to the product table and update it whenever price or quantity changes.
  • Reasoning: This avoids recalculating total_price every time you query the table, significantly speeding up those queries.
  • Trade-off: You now have redundant data. You must ensure that the total_price column is always consistent with the price and quantity. This adds complexity to updates and inserts.

2. Combining Tables:

  • Scenario: You have Customers and Orders tables (as in the previous example). You frequently need to retrieve customer information along with their order details.
  • Normalization: You would use a JOIN to combine the tables in your queries.
  • Denormalization: You could add some customer information (e.g., customer_name, city) directly to the Orders table.
  • Reasoning: Eliminates the need for joins, which can be expensive, especially with large tables. This speeds up queries that retrieve both customer and order information.
  • Trade-off: Customer data is now duplicated in the Orders table. If a customer's name or city changes, you need to update it in multiple places.

3. Adding Redundant Data for Reporting:

  • Scenario: You have a sales database and need to generate monthly sales reports by region.
  • Normalization: You might have separate tables for sales transactions, products, customers, and regions.
  • Denormalization: You could add the region information directly to the sales transactions table.
  • Reasoning: Simplifies report generation queries. You no longer need to join multiple tables to group sales by region.
  • Trade-off: Redundant region data in the sales table.

4. Creating Summary Tables (Materialized Views):

  • Scenario: You have a large fact table in a data warehouse, and you frequently need to perform aggregations (e.g., sums, averages) over it.
  • Normalization: Aggregations are calculated on the fly during query execution.
  • Denormalization: You could create a summary table (also known as a materialized view) that pre-calculates and stores these aggregations.
  • Reasoning: Dramatically speeds up the retrieval of aggregated data.
  • Trade-off: The summary table needs to be updated whenever the underlying fact table changes. This adds complexity and storage overhead.

5. Handling Historical Data:

  • Scenario: You track customer addresses, and addresses can change over time.
  • Normalization: You might have a separate table to store address history.
  • Denormalization: For certain reporting or analytical purposes, you might want to "snapshot" the customer's address at the time of each transaction and store it directly with the transaction data.
  • Reasoning: Simplifies analysis of historical data ("what was the customer's address when they placed this order?").
  • Trade-off: More data storage, and the risk of inconsistencies if address changes are not handled carefully.

When to Denormalize:

Denormalization should be considered carefully and only when the performance benefits outweigh the risks to data integrity. It's often used in these situations:

  • Read-heavy workloads: Where read performance is critical (e.g., data warehouses, reporting systems).
  • Complex queries: Where joins or aggregations are computationally expensive.
  • Specific performance bottlenecks: Where profiling has identified specific queries that are slowing down the system.

Important Considerations:

  • Data consistency: You must implement mechanisms to ensure that redundant data is kept consistent. This often involves triggers or application logic.
  • Storage space: Denormalization increases storage space requirements.
  • Update complexity: Updates become more complex because you might need to update data in multiple places.

In summary, denormalization is a technique to improve performance by strategically adding redundancy. It's a trade-off that should be carefully evaluated based on the specific needs of your application. It's generally better to start with a normalized design and only denormalize when necessary.
