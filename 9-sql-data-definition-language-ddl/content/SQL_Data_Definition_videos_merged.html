Introduction to SQL DDL

Introduction

SQL is often described as a single language, but in practice it is a family of related sublanguages, each with a different job. Data Definition Language (DDL) is the part of SQL used to create and shape the structures that hold your data: tables, columns, data types, constraints, indexes, views, and schemas. Commands such as CREATE, ALTER, DROP, and TRUNCATE belong to DDL, and together they define what a database can store and what rules the stored data must obey.

This distinction matters in COP4708 because almost everything else you do depends on it. Queries written with SELECT (DQL) and data changes made with INSERT, UPDATE, and DELETE (DML) can only work within the structure that DDL has already established. Permissions (DCL) and transaction control (TCL) round out the picture. Getting comfortable naming these categories now will make the rest of the module, where you write real CREATE TABLE and ALTER TABLE statements, much easier to follow.

As you watch the videos below, keep a running list of which commands fall into which sublanguage, and notice how often DDL decisions, such as choosing a data type or adding a constraint, are decisions about data integrity rather than just syntax. Also pay attention to the commands that permanently change or remove structures, since those are the ones with the most serious consequences in a live database.

The CREATE Command

Introduction

The CREATE statement is the starting point of SQL's Data Definition Language (DDL). While queries with SELECT read data that already exists, DDL commands build and shape the containers that hold data: databases, schemas, and tables. In this topic you will work through that hierarchy from the outside in — creating a database, organizing objects into a schema, and then defining individual tables with named columns and data types.

This matters in COP4708 because everything you have designed on paper so far — entities, attributes, relationships — eventually has to be expressed as runnable SQL. A well-written CREATE TABLE statement captures your design decisions: what each column is called, what kind of values it may hold, how wide or precise those values are, and which schema the table belongs to. Poor choices here (a text column for a date, an undersized character field, inconsistent naming) are costly to fix once data is loaded.

As you watch, pay attention to three things: the exact syntax and punctuation of a CREATE statement, how the presenter chooses a data type for each column and justifies it, and how fully qualified names (schema.table) are used. Also notice that syntax varies a little between database products such as MySQL, Oracle, SQL Server, and PostgreSQL, so confirm the dialect your course environment uses before you run anything.

Data Types and Column Definitions

Introduction

Every column in a relational table has a data type, and that type is a promise about what the column may hold. Numeric types (INT, SMALLINT, BIGINT, DECIMAL/NUMERIC, FLOAT), character and string types (CHAR, VARCHAR, TEXT), date and time types (DATE, TIME, TIMESTAMP), and boolean or binary types (BOOLEAN, BLOB/BINARY) each store values differently and allow different operations. Choosing DECIMAL instead of FLOAT for currency, or DATE instead of VARCHAR for a birthdate, is not a stylistic preference — it determines whether the database can validate, sort, compare, and compute on your data correctly.

In this module you write CREATE TABLE statements, and the column definition is where the data type lives: a column name, a type (often with a length or precision, such as VARCHAR(50) or DECIMAL(10,2)), and any column-level constraints such as NOT NULL or DEFAULT. Data types are the first line of defense for data integrity; constraints build on top of them. Keep in mind that exact type names vary by DBMS (MySQL, SQL Server, Oracle, PostgreSQL, SQLite), so expect small differences between videos and your course environment.

As you watch, note three things: which type each presenter chooses for a given kind of value and why, how length or precision is specified, and how the data type sits alongside constraints inside the parentheses of a CREATE TABLE statement. Jot down any type names that differ from the ones your course uses so you can map them later.

Constraints in SQL

Introduction

Constraints are the rules you attach to a table so the database itself refuses to store bad data. A PRIMARY KEY guarantees that every row can be uniquely identified (and that the key column is never empty), a FOREIGN KEY ties a column in one table to the key of another so relationships stay valid, NOT NULL forces a value to be supplied, UNIQUE blocks duplicate values in a column that is not the primary key, and DEFAULT supplies a value automatically when the INSERT statement leaves the column out. Together these are the backbone of relational integrity.

In this module you are learning Data Definition Language, and constraints are written directly into the CREATE TABLE statement alongside column names and data types. That makes them a design decision, not an afterthought: if you declare them correctly up front, the database enforces your business rules on every insert and update from then on. You will also see that constraints can be added, renamed, or dropped later with ALTER TABLE when requirements change.

As you watch the videos below, pay attention to the exact syntax and placement of each constraint (column-level versus table-level), to how a foreign key names the parent table and column it references, and to what the database actually does when a statement violates a rule. Note also that the examples come from CockroachDB, a PostgreSQL-compatible SQL database, so the ideas transfer directly but minor syntax details may vary from the DBMS you use in class.

The ALTER Command

Introduction

Database designs rarely stay the same once an application goes live. Requirements change, new data needs to be captured, and mistakes in the original schema have to be corrected. The ALTER TABLE command is the SQL Data Definition Language tool that lets you change the structure of a table that already exists — adding a column, changing a column's data type or size, removing a column, and adding or dropping constraints such as PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, and CHECK.

What makes ALTER TABLE important in this course is that it changes structure without discarding the rows already stored. That is the key difference between altering a table and dropping and recreating it. It also means you have to think about the existing data: adding a NOT NULL column to a populated table, shrinking a column's size, or adding a foreign key when some rows hold values that do not exist in the parent table can all fail or require extra steps.

As you watch the videos below, pay attention to the exact clause keywords used (ADD, ALTER COLUMN or MODIFY, DROP COLUMN, ADD CONSTRAINT, DROP CONSTRAINT), to how constraints are given names so they can be dropped later, and to any differences in syntax between SQL Server and MySQL. Try reproducing each statement on a small test table of your own so you can see what happens to the rows that were already there.

The DROP and TRUNCATE Commands

Introduction

So far in this module you have been building database objects: creating tables, defining data types, applying constraints, and altering structures that already exist. This topic looks at the other side of data definition — removing things. DROP is the DDL command that permanently deletes a database object such as a table, view, schema, or even an entire database, taking its structure and its data with it. TRUNCATE is a related command that keeps the table definition intact but removes every row in one fast operation.

The reason these two commands get their own topic is that they are easy to confuse with each other and with DELETE, a DML command that removes rows based on a WHERE condition. The three differ in what they affect (object vs. rows), how they are logged, whether they can be rolled back, how they interact with identity/auto-increment counters and foreign key references, and how quickly they run on large tables. Choosing the wrong one in a production database is one of the classic ways to lose data permanently.

As you watch the videos below, keep a comparison table in front of you and fill in columns for DROP, TRUNCATE, and DELETE: Does the table still exist afterward? Can you filter which rows go? Is it DDL or DML? Can it be undone? What happens to constraints and identity seeds? Also pay attention to the syntax each presenter types — note how short and unforgiving these statements are, which is exactly why best practices like backups, testing on a copy, and double-checking the database context matter.

Working with Schemas

Introduction

A database schema is a named logical container that groups related tables, views, indexes, and other objects inside a database. Instead of dumping every table into one undifferentiated space, you can create a schema such as sales or hr and place the objects that belong to that area of the business inside it. Because object names only need to be unique within a schema, two different schemas can each hold a table called ORDERS without conflict.

In this module you will practice the statements that make this work: CREATE SCHEMA to define the container, schema-qualified names such as sales.orders to refer to an object unambiguously, CREATE TABLE statements written inside a chosen schema, and DROP SCHEMA to remove one (with care, since dropping a schema can take its contents with it). Keep in mind that different database systems treat schemas slightly differently — in Oracle a schema is tied to a user account, while in PostgreSQL and SQL Server a schema is a separate namespace you create explicitly — so always check which product you are writing for.

As you watch the videos below, pay attention to two things. First, notice how objects are named and referenced: when does the writer use a bare table name and when does a prefix appear? Second, notice how design decisions — which tables exist and how they relate — naturally suggest which objects belong together, which is exactly the organizational benefit schemas provide.
