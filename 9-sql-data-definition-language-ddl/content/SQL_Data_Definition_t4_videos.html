Introduction

Constraints are the rules you attach to a table so the database itself refuses to store bad data. A PRIMARY KEY guarantees that every row can be uniquely identified (and that the key column is never empty), a FOREIGN KEY ties a column in one table to the key of another so relationships stay valid, NOT NULL forces a value to be supplied, UNIQUE blocks duplicate values in a column that is not the primary key, and DEFAULT supplies a value automatically when the INSERT statement leaves the column out. Together these are the backbone of relational integrity.

In this module you are learning Data Definition Language, and constraints are written directly into the CREATE TABLE statement alongside column names and data types. That makes them a design decision, not an afterthought: if you declare them correctly up front, the database enforces your business rules on every insert and update from then on. You will also see that constraints can be added, renamed, or dropped later with ALTER TABLE when requirements change.

As you watch the videos below, pay attention to the exact syntax and placement of each constraint (column-level versus table-level), to how a foreign key names the parent table and column it references, and to what the database actually does when a statement violates a rule. Note also that the examples come from CockroachDB, a PostgreSQL-compatible SQL database, so the ideas transfer directly but minor syntax details may vary from the DBMS you use in class.
