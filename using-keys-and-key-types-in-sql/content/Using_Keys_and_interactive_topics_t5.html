Composite Keys

▶

In relational database design, a primary key is the mechanism that guarantees every row in a table can be uniquely identified. Most introductory examples show a single column — an auto-incrementing integer or a UUID — filling that role. In practice, however, many tables describe relationships or events where no single column on its own is enough to tell two rows apart. A composite key solves this problem by combining two or more columns into a single logical unit of identification. The database engine treats the combination of those columns as the key, so uniqueness and identity are evaluated across all of them together, never in isolation.

Understanding composite keys well requires exploring not just their syntax but also the reasoning that drives their use, the constraints that govern them, and the practical trade-offs they introduce in schema design, query writing, and index management.

What Is a Composite Key?

A composite key is any key — primary or unique — that is defined over two or more columns. Consider a table that records which students are enrolled in which courses. A single student can appear in many courses, and a single course can contain many students, so neither student_id alone nor course_id alone is unique across the table. The pair (student_id, course_id), however, should appear at most once: a student either is or is not enrolled in a given course. That pair is the natural composite primary key.

-- A simple enrollment junction table with a composite primary key
CREATE TABLE enrollment (
    student_id  INT  NOT NULL,
    course_id   INT  NOT NULL,
    enrolled_on DATE NOT NULL,
    PRIMARY KEY (student_id, course_id)
);

The database now enforces that the same (student_id, course_id) combination cannot appear twice, even though each individual column value may repeat many times. All columns that form the composite key are treated as a single logical unit: insert, update, and uniqueness checks all operate on the tuple as a whole.

Composite keys appear most frequently in junction tables (also called association tables or bridge tables) that resolve many-to-many relationships. Every row in such a table represents a unique pairing — a student and a course, an employee and a project, a product and an order — and the composite of the two foreign-key columns is typically the natural primary key.

When to Use a Composite Key

The decision between a composite key and a surrogate single-column key is partly a matter of style and partly a matter of business logic. There are clear situations where a composite key is the better choice.

  • When the combination carries real-world meaning. If two attributes together are guaranteed unique by a business rule — a flight number plus a departure date, a national tax ID plus a country code, a warehouse location code plus a bin number — that combination is a natural key. Using it as the composite primary key makes the uniqueness rule visible in the schema itself rather than hidden behind an opaque surrogate integer.
  • When a surrogate key would obscure business logic. Adding an auto-increment column to an enrollment table technically works, but it allows inserting a duplicate (student_id, course_id) pair unless a separate unique constraint is also added. With a composite primary key, the constraint is intrinsic to the key itself.
  • In intersection tables. Every well-formed junction table resolving a many-to-many relationship has a natural composite key made up of the two (or more) foreign keys it contains. Using those foreign keys as the composite primary key is standard practice because it simultaneously enforces the uniqueness of each pairing and documents the table's purpose.
  • When no suitable surrogate exists or adding one is costly. Legacy schemas, imported data sets, or certain regulatory reporting tables may not have a convenient place to add an extra column. A composite key over existing meaningful columns avoids schema changes.

Conversely, if the combination of columns is likely to change over time (because business rules evolve), or if the table will be referenced by many child tables (making every foreign key verbose), a surrogate key paired with a composite unique constraint is often a cleaner long-term design.

Defining a Composite Primary Key in SQL

SQL syntax for a composite primary key requires the constraint to be declared at the table level, not the column level. A column-level PRIMARY KEY keyword can only designate a single column; to span multiple columns, the PRIMARY KEY clause must appear separately after all the column definitions.

-- CORRECT: table-level composite primary key
CREATE TABLE order_item (
    order_id    INT           NOT NULL,
    product_id  INT           NOT NULL,
    quantity    INT           NOT NULL DEFAULT 1,
    unit_price  NUMERIC(10,2) NOT NULL,
    PRIMARY KEY (order_id, product_id)   -- table-level constraint
);

-- INCORRECT: attempting column-level syntax for a composite key
CREATE TABLE order_item (
    order_id   INT NOT NULL PRIMARY KEY,  -- this alone is only one column
    product_id INT NOT NULL PRIMARY KEY,  -- most databases raise an error here
    quantity   INT NOT NULL
);

Several important rules govern composite primary keys:

  • Implicit NOT NULL. Every column that participates in a primary key — composite or single — is automatically treated as NOT NULL. NULL cannot participate in a uniqueness comparison in standard SQL (NULL is not equal to anything, including itself), so the database prohibits NULL values in key columns even if you forget to write NOT NULL explicitly. It is good practice to write it explicitly anyway, for readability.
  • Column order matters for performance. The database builds a B-tree index over the composite key in the order the columns are listed. Queries that filter on the leading column(s) of the key can use that index efficiently; queries that filter only on a trailing column typically cannot. List columns in the order that reflects the most common access pattern. In an enrollment table queried most often by student, PRIMARY KEY (student_id, course_id) is preferable to the reverse order.
  • One primary key per table. A table can have only one primary key, composite or otherwise. Additional uniqueness requirements must be expressed as UNIQUE constraints.

The following example shows a time-series sensor reading table where the sensor identifier and the timestamp together form the natural composite key:

CREATE TABLE sensor_reading (
    sensor_id    CHAR(8)          NOT NULL,
    recorded_at  TIMESTAMP        NOT NULL,
    temperature  NUMERIC(5,2),
    humidity     NUMERIC(5,2),
    PRIMARY KEY (sensor_id, recorded_at)
);

A new reading for sensor 'SENS0042' at a timestamp that already exists in the table will be rejected, preventing accidental duplicate records for the same sensor at the same moment.

Defining a Composite Unique Constraint

A composite unique constraint enforces the same combination-of-values uniqueness as a composite primary key, but without designating those columns as the table's primary identifier. This is useful when a table already has a surrogate primary key but the schema must also enforce a business rule that spans multiple columns.

CREATE TABLE employee (
    employee_id   SERIAL        PRIMARY KEY,          -- surrogate key
    department_id INT           NOT NULL,
    badge_number  VARCHAR(20)   NOT NULL,
    full_name     VARCHAR(100)  NOT NULL,
    UNIQUE (department_id, badge_number)              -- composite unique constraint
);

This says: within a given department, no two employees may share the same badge number, but the same badge number can repeat across different departments. The composite unique constraint captures that business rule precisely.

Key differences between a composite unique constraint and a composite primary key:

Characteristic Composite Primary Key Composite Unique Constraint
NULL values allowed No — all columns implicitly NOT NULL Yes — NULL is typically permitted; two rows each containing NULL in the same column are generally not considered duplicates under SQL's three-valued logic
Number per table Exactly one Multiple allowed
Backing index Always created (clustered in some engines) Always created (non-clustered by default)
Can be referenced by a foreign key Yes Yes (in most databases)
Communicates row identity Yes — this IS the row identifier No — expresses a business rule, not identity

A table may carry several composite unique constraints simultaneously, each enforcing a different business rule:

CREATE TABLE vehicle_registration (
    reg_id         SERIAL       PRIMARY KEY,
    vin            CHAR(17)     NOT NULL,
    license_plate  VARCHAR(10)  NOT NULL,
    state_code     CHAR(2)      NOT NULL,
    owner_id       INT          NOT NULL,
    UNIQUE (vin),                              -- VIN is globally unique on its own
    UNIQUE (license_plate, state_code)         -- plate+state unique together
);

Referencing a Composite Key with Foreign Keys

When a child table needs to reference a parent table whose primary key is composite, the foreign key declaration must name every column of that composite key and list them in the same order as the parent's primary key definition.

-- Parent table: composite primary key
CREATE TABLE project_assignment (
    employee_id  INT  NOT NULL,
    project_id   INT  NOT NULL,
    role         VARCHAR(50),
    PRIMARY KEY (employee_id, project_id)
);

-- Child table: composite foreign key referencing the parent
CREATE TABLE assignment_log (
    log_id       SERIAL       PRIMARY KEY,
    employee_id  INT          NOT NULL,
    project_id   INT          NOT NULL,
    logged_at    TIMESTAMP    NOT NULL DEFAULT NOW(),
    note         TEXT,
    FOREIGN KEY (employee_id, project_id)
        REFERENCES project_assignment (employee_id, project_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
);

Several rules apply to composite foreign keys:

  • Column count must match exactly. If the parent's composite key has three columns, the child's foreign key clause must also list three columns. A mismatch causes a schema error.
  • Data types must match exactly. If employee_id is INT in the parent, it must be INT in the child. Mixing INT and BIGINT, for instance, typically raises an error or at least a warning depending on the database engine.
  • Referential actions apply to the tuple. ON DELETE CASCADE, ON UPDATE CASCADE, SET NULL, and RESTRICT all operate on the combination. Deleting a row in project_assignment will cascade-delete every matching row in assignment_log based on the full (employee_id, project_id) pair.
  • NULL behavior. If any column in the child's composite foreign key is NULL, most databases skip the referential integrity check for that row entirely, treating the partial NULL as meaning "no parent referenced."

Advantages and Limitations of Composite Keys

Like every design choice, composite keys come with genuine benefits and real costs. Weighing them carefully leads to better schema decisions.

Advantages:

  • No extra surrogate column needed. When the data already contains a naturally unique combination of attributes, using that combination as the primary key avoids adding an artificial column that serves no business purpose. The schema stays lean and honest.
  • Self-documenting constraints. A composite primary key on (student_id, course_id) tells any reader immediately that each student-course pairing is unique. The business rule is encoded in the structure, not buried in application code or a comment.
  • Stronger data integrity guarantees. Because the composite key constraint is enforced at the database level, no application code path — no matter how buggy — can insert a duplicate pairing. Surrogate keys paired with separate unique constraints provide the same guarantee, but the composite key approach provides it in a single declaration.
  • Efficient covering indexes. A composite key index that includes all columns needed by a common query can satisfy that query entirely from the index without touching the base table (an index-only scan), which can significantly improve read performance.

Limitations:

  • Verbose joins and foreign keys. Every join against a table with a composite key must list all participating columns in the ON clause. Every foreign key referencing it must declare all columns. As the number of key columns grows, SQL statements become longer and more error-prone.
-- Join with a two-column composite key — manageable
SELECT al.logged_at, al.note
FROM   assignment_log al
JOIN   project_assignment pa
  ON   al.employee_id = pa.employee_id
 AND   al.project_id  = pa.project_id;
  • Larger indexes. An index on two or three columns consumes significantly more disk space and memory than a single-column integer index. For very large tables this can affect both storage costs and the speed of index maintenance during inserts and updates.
  • Column ordering sensitivity. The leading column of a composite index is critical. An index on (student_id, course_id) accelerates lookups by student but provides limited help for lookups by course alone. If both access patterns are equally common, a separate index on the trailing column(s) may be necessary, adding further overhead.
  • Cascading changes can be complex. If a composite key column's value needs to change — for example, a business rekeys its department codes — the update must propagate through every foreign key relationship that references it, touching multiple columns simultaneously. Surrogate integer keys, being meaningless by design, rarely need to change.
  • ORM and framework compatibility. Some object-relational mapping tools handle composite keys less elegantly than single-column surrogate keys, requiring additional configuration. This is a practical (not theoretical) consideration when choosing a key strategy.

The table below summarizes the comparison between a pure composite natural key approach and a surrogate-key-plus-unique-constraint approach for a junction table:

Concern Composite Primary Key Surrogate PK + Composite UNIQUE
Schema simplicity Fewer columns; no surrogate needed One extra column (the surrogate)
Business rule visibility Encoded directly in PK Encoded in separate UNIQUE constraint
Foreign key verbosity All key columns must be repeated in every child Only the surrogate integer is referenced
Index size Larger (multi-column key) Smaller PK index; separate UNIQUE index adds cost
Key stability Fragile if key column values change Surrogate never changes; stable references
ORM support Varies; often requires explicit mapping Generally straightforward

In summary, composite keys are a powerful, expressive tool in relational schema design. They are the natural solution for junction tables and for data that carries inherent multi-attribute uniqueness guarantees. Used thoughtfully — with attention to column ordering, data-type consistency, and the verbosity they introduce in child tables and joins — they produce schemas that are both correct and self-explanatory.
