Candidate Keys

▶

In relational database theory, a candidate key is any column — or minimal combination of columns — in a table that is capable of uniquely identifying every row. The word "candidate" is deliberate: each such key is a contender for the role of primary key. Exactly one candidate key is ultimately promoted to primary key status, but the others do not disappear from the design; they remain meaningful structural constraints that protect data integrity. Understanding candidate keys thoroughly is essential because they sit at the very heart of relational theory, normalization, and sound schema design.

Before exploring the formal properties, consider a concrete scenario. Imagine a university maintains a table of enrolled students. Every student is assigned a system-generated student number, and every student also has a government-issued national identity number. Both columns uniquely identify a student with no duplicates and no missing values. Both are therefore candidate keys. The designer must choose one as the primary key, but both deserve to be treated as keys throughout the lifetime of the database.

What Is a Candidate Key?

A candidate key is defined by two non-negotiable requirements: its values must be unique across every row in the table, and it must never contain NULL values. These two requirements work together. Uniqueness alone is not enough — if a column can be NULL, two different rows could both have NULL in that column, making it impossible to tell them apart through the key. NULL represents an unknown or inapplicable value, so a key that permits NULL cannot guarantee that every single row is fully and unambiguously identifiable.

Consider the following students table:

student_number national_id email full_name
1001NI-884-221ana@uni.eduAna Rivera
1002NI-553-019ben@uni.eduBen Okoro
1003NI-771-340cara@uni.eduCara Singh

Here, student_number, national_id, and email each appear to be unique across all current rows. Whether each qualifies as a true candidate key depends on whether that uniqueness is a guaranteed structural property — not a coincidence of the current data snapshot — and whether NULLs are permitted. If the business rules state that every student must have a student number, a national ID, and an email, and all three must be unique system-wide, then all three are candidate keys.

Properties That Define a Candidate Key

Two formal properties must both be satisfied simultaneously for a set of columns to qualify as a candidate key:

  • Uniqueness: No two rows in the table may share the same value (or the same combination of values, in the case of a composite key) for the candidate key columns. This uniqueness must be a permanent guarantee enforced by the database schema, not merely a characteristic of the rows that happen to exist today. For example, if full_name is unique in the current data only because the university happens to have no name collisions right now, it is not a candidate key — the domain knowledge tells us that two students could share the same name in the future.
  • Irreducibility (Minimality): No proper subset of the key's columns can provide the same uniqueness guarantee on its own. This property is what distinguishes a candidate key from a mere superkey. A superkey is any set of columns that uniquely identifies rows, including sets with redundant columns. A candidate key is a superkey stripped down to its smallest irreducible form. For example, if student_number alone uniquely identifies every student, then the combination (student_number, email) is a superkey but not a candidate key, because email is unnecessary for uniqueness.

Consider a course_enrollments table that records which student is enrolled in which course in which semester:

student_number course_code semester grade
1001CS1012024-FallA
1001MA2012024-FallB
1002CS1012024-FallA
1001CS1012025-SpringNULL

No single column is unique here — student 1001 appears multiple times, course CS101 appears multiple times, and semester 2024-Fall appears multiple times. The combination (student_number, course_code, semester) is unique across all rows: a student can enroll in the same course in different semesters, but not twice in the same semester for the same course. Dropping any one of the three columns breaks uniqueness. Therefore, (student_number, course_code, semester) is a candidate key — specifically a composite candidate key.

Identifying Candidate Keys in a Table

The process of identifying candidate keys involves both mechanical testing and informed reasoning about the domain:

  • Examine single columns first. For each column, ask whether its values are required to be unique and non-NULL for every possible valid row — not just the rows currently in the table. Columns like sequential IDs, government ID numbers, email addresses (when required and unique by policy), or ISBN numbers for books are strong candidates. Columns like names, dates, or status codes are almost never candidate keys on their own.
  • Test combinations of columns when no single column qualifies. When no individual column passes the uniqueness test, look for pairs or larger groups. Begin with the smallest combinations and work outward. A combination qualifies only if no smaller subset of it also provides uniqueness — this enforces the minimality requirement.
  • Apply domain knowledge and business rules. This is the most important step. Current data can be misleading. A column might happen to contain all unique values in a table with ten rows, but the business rules might allow duplicates. Conversely, a business rule might guarantee uniqueness even though duplicate values could theoretically arise — for example, a business rule stating "no two products may share the same SKU code." Always reason about the universe of all valid future states of the table, not just what is stored today.

A practical example: suppose you are designing a table for a product catalog.

product_id sku barcode product_name price
1SKU-0015901234123457Wireless Mouse29.99
2SKU-0024006381333931USB Keyboard49.99
3SKU-0037350053850019HDMI Cable12.99

Domain knowledge tells us: product_id is a system-generated surrogate that is always unique and never NULL; sku is a mandatory, unique stock-keeping code assigned by the business; barcode is a mandatory, globally unique product barcode. product_name could theoretically repeat (two different products might share a generic name), and price obviously repeats. Therefore, product_id, sku, and barcode are all candidate keys. The combination (sku, barcode) would be a superkey but not a candidate key, because each column alone already guarantees uniqueness.

Candidate Keys vs. Primary Keys

The relationship between candidate keys and the primary key is straightforward but important to be precise about. The primary key is simply the one candidate key that the database designer formally designates as the main mechanism for identifying rows. It is declared with the PRIMARY KEY constraint in SQL, and it serves as the target of foreign key references from other tables. Only one primary key is permitted per table.

The candidate keys that are not chosen as the primary key are sometimes called alternate keys. They are just as valid from a theoretical standpoint — they still uniquely identify every row — but they play a supporting role in the schema. The choice of which candidate key to promote to primary key is a design decision, not a theoretical one. Designers typically favor:

  • Simplicity: A single-column key is easier to work with as a foreign key than a composite key.
  • Stability: A key whose value is unlikely to change over time is preferable. A student's email address might change; a system-generated student number typically does not.
  • Performance: Shorter keys (such as integers) are indexed and compared more efficiently than longer strings like email addresses or barcodes.

In the product catalog example, a designer would likely choose product_id as the primary key because it is a compact integer that never changes. The sku and barcode columns would be enforced as alternate keys using UNIQUE constraints.

Enforcing Candidate Keys with UNIQUE Constraints

Because only one candidate key can become the primary key, the others must be enforced through UNIQUE constraints. A UNIQUE constraint tells the database engine that no two rows may hold the same value (or combination of values) in the constrained column or columns. This preserves the integrity of alternate keys at the database level, ensuring that the uniqueness guarantee is not merely a convention documented in design notes but is actively enforced at every insert and update.

The SQL to enforce the product catalog's candidate keys might look like this:

CREATE TABLE products (
    product_id  INT          NOT NULL,
    sku         VARCHAR(20)  NOT NULL,
    barcode     VARCHAR(20)  NOT NULL,
    product_name VARCHAR(100) NOT NULL,
    price       DECIMAL(10,2) NOT NULL,
    CONSTRAINT pk_products PRIMARY KEY (product_id),
    CONSTRAINT uq_products_sku UNIQUE (sku),
    CONSTRAINT uq_products_barcode UNIQUE (barcode)
);

There is one important distinction between the PRIMARY KEY and UNIQUE constraints regarding NULL values. A PRIMARY KEY column always prohibits NULLs — this is absolute. A UNIQUE constraint, in most relational database systems (including PostgreSQL, MySQL, and SQL Server), permits NULL values in the constrained column, and typically allows multiple rows to each have NULL in that column. The reasoning is that NULL means "unknown," and two unknown values are not considered equal, so they do not violate uniqueness. However, this behavior means a UNIQUE column with NULLs does not fully satisfy the theoretical definition of a candidate key, which requires non-NULL values in every row. To enforce a true alternate key using a UNIQUE constraint, the column should also be declared NOT NULL, as shown in the example above.

For composite alternate keys, the UNIQUE constraint covers the combination:

ALTER TABLE course_enrollments
    ADD CONSTRAINT uq_enrollment UNIQUE (student_number, course_code, semester);

This ensures the combination is unique across all rows, mirroring the uniqueness guarantee that a composite primary key would provide.

Role of Candidate Keys in Database Design

Candidate keys are not just a bookkeeping formality — they play active, foundational roles in the entire design and optimization of a relational database.

  • Foundation for normalization: The normal forms that drive redundancy elimination — particularly Second Normal Form (2NF) and Third Normal Form (3NF) — are defined in terms of functional dependencies relative to candidate keys, not just the primary key. A non-key attribute that depends on only part of a composite candidate key violates 2NF regardless of which key was chosen as primary. Designers who ignore alternate candidate keys risk creating schemas with hidden redundancy and update anomalies. Recognizing all candidate keys is therefore a prerequisite for a correctly normalized schema.
  • Design flexibility: Having multiple candidate keys gives the designer choices. If business requirements change — for example, the government stops issuing national identity numbers in the same format — the designer can promote a different candidate key to primary key status, or adjust the schema with confidence because the underlying uniqueness structure was already understood and enforced.
  • Index creation and query performance: Columns that form candidate keys are excellent candidates for database indexes. Because their values are unique, indexes built on them are maximally selective — a query filtering on a candidate key column can locate a single row with minimal index traversal. Most database engines automatically create an index when a PRIMARY KEY or UNIQUE constraint is declared, so enforcing candidate keys through constraints also brings automatic performance benefits. For large tables, having a unique index on a frequently queried column (like email or barcode) can reduce query execution time from a full table scan to an almost instant lookup.
  • Data integrity at every layer: Enforcing all candidate keys — not just the primary key — closes the door on subtle data integrity problems. For example, if a business rule says every customer must have a unique email address but only the primary key (a surrogate ID) is enforced in the database, nothing prevents two rows for different customers from sharing the same email address. Declaring a UNIQUE NOT NULL constraint on the email column enforces the candidate key and prevents this class of error entirely, regardless of whether the application layer remembers to check.

To summarize the relationships discussed, the following table contrasts the key concepts:

Concept Definition Allows NULL? How Many Per Table? Enforced By

Mastering candidate keys means understanding that the primary key is not the only key that matters — it is simply the chosen representative of a potentially richer set of uniqueness guarantees that exist in the data. Identifying, documenting, and enforcing all candidate keys produces schemas that are more robust, more flexible, and better aligned with the real-world business rules the database is meant to serve.
