Foreign Keys and Referential Integrity

▶

In a relational database, data is deliberately spread across multiple tables to reduce redundancy and keep each table focused on a single subject. The power of this design, however, depends entirely on the ability to connect those tables in a reliable and consistent way. Foreign keys are the mechanism that makes those connections formal and enforceable. A foreign key is a column, or a set of columns, in one table whose values correspond to the values of a primary key (or unique key) in another table. By declaring a foreign key constraint, you instruct the database engine to guarantee that any value stored in the foreign key column actually exists in the referenced table — and that no action will silently break that guarantee.

This kind of guarantee is called referential integrity, and it is one of the foundational rules of the relational model. Without it, rows in a child table could point to parent rows that no longer exist — so-called "orphan" records — leading to corrupted query results, broken application logic, and data that cannot be trusted. Understanding foreign keys therefore means understanding not just the syntax to define them, but the full lifecycle of constraints: what they prevent, what automatic actions they can trigger, and how NULL values interact with them.

What Is a Foreign Key?

A foreign key is defined in the context of a relationship between two tables. Consider a classic example: an orders table and a customers table. Every order belongs to exactly one customer, so the orders table stores a customer_id column whose value must match an existing customer_id in the customers table. The customer_id in orders is the foreign key.

Several key properties define how foreign keys behave:

  • No uniqueness requirement on the referencing side. Unlike a primary key, a foreign key column does not need to hold unique values. Many rows in the orders table can share the same customer_id — this is precisely how a one-to-many relationship is expressed. Customer 42 can appear in hundreds of order rows; that is entirely valid. The uniqueness requirement belongs to the parent table's primary key, not to the child's foreign key.
  • Child table and parent table roles. The table that contains the foreign key is called the child table (also called the referencing table). The table whose primary key is being pointed to is the parent table (also called the referenced table). In the example above, orders is the child and customers is the parent. Deletions and updates on the parent side are the operations that most directly stress referential integrity, because removing a parent row can leave child rows without a valid reference.
  • Composite foreign keys. When a parent table's primary key spans more than one column — a composite primary key — the foreign key must mirror that structure exactly. If a shipments table references a warehouse_inventory table whose primary key is (warehouse_id, product_id), then the shipments table must carry both a warehouse_id and a product_id column, declared together as a single composite foreign key. The number of columns, their order, and their data types must all match.

Defining a Foreign Key Constraint in SQL

Foreign key constraints can be written either inline within a CREATE TABLE statement or added to an existing table with ALTER TABLE. Both approaches produce identical constraints at the database level.

The most common pattern — declaring the constraint at table creation — looks like this:

CREATE TABLE customers (
    customer_id   INT          PRIMARY KEY,
    full_name     VARCHAR(100) NOT NULL,
    email         VARCHAR(150) NOT NULL
);

CREATE TABLE orders (
    order_id      INT          PRIMARY KEY,
    order_date    DATE         NOT NULL,
    customer_id   INT          NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers (customer_id)
);

Breaking down the syntax:

  • CONSTRAINT fk_orders_customer gives the constraint a meaningful name. Naming constraints is optional in some databases but strongly recommended because it makes error messages and future ALTER TABLE operations far easier to read and maintain.
  • FOREIGN KEY (customer_id) identifies the column in the child table that holds the foreign key values.
  • REFERENCES customers (customer_id) uses the REFERENCES keyword to name the parent table and, in parentheses, the specific column being referenced. The referenced column must be the primary key or a unique key of the parent table.

If the table already exists and you need to add the constraint later, the ALTER TABLE ... ADD CONSTRAINT syntax is used:

ALTER TABLE orders
    ADD CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers (customer_id);

One critical rule applies in both cases: the data types of the foreign key column and the referenced primary key column must be compatible. An INT foreign key referencing an INT primary key works perfectly. Mixing INT with VARCHAR, or signed with unsigned integers, will cause the database to reject the constraint definition. This type-compatibility requirement is not just a syntax rule — it reflects the logical requirement that comparison between the two columns must be meaningful.

For a composite example, suppose a parent table uses a two-column primary key:

CREATE TABLE warehouse_inventory (
    warehouse_id  INT         NOT NULL,
    product_id    INT         NOT NULL,
    quantity      INT         NOT NULL,
    PRIMARY KEY (warehouse_id, product_id)
);

CREATE TABLE shipments (
    shipment_id   INT         PRIMARY KEY,
    warehouse_id  INT         NOT NULL,
    product_id    INT         NOT NULL,
    units_shipped INT         NOT NULL,
    CONSTRAINT fk_shipments_inventory
        FOREIGN KEY (warehouse_id, product_id)
        REFERENCES warehouse_inventory (warehouse_id, product_id)
);

Notice that the column order inside FOREIGN KEY (...) and REFERENCES ... (...) must correspond positionally — the first column maps to the first, the second to the second, and so on.

Understanding Referential Integrity

Referential integrity is the rule that every non-NULL foreign key value in a child table must match an existing primary key value in the parent table. The database enforces this rule automatically on every data-modification operation that could threaten it. There are two directions in which integrity can be violated, and the constraint guards against both.

  • INSERT and UPDATE on the child table. If an application tries to insert a row into orders with a customer_id of 999, but no customer with that ID exists in customers, the database raises an error and rejects the operation. The same applies to an UPDATE that would change a customer_id to a non-existent value. This prevents orphaned child rows from being created in the first place.
  • DELETE and UPDATE on the parent table. If a customer with customer_id = 5 has associated orders in the orders table, a plain DELETE FROM customers WHERE customer_id = 5 would leave those order rows pointing at a customer that no longer exists. By default, the database blocks this operation. The same applies to an UPDATE that changes the primary key value of the parent row — the child rows would still hold the old value.

Enforcing referential integrity consistently across all tables ensures that JOIN queries produce meaningful, accurate results, that application-level assumptions about data relationships hold true, and that analytical reports built on the database reflect reality rather than artifacts of incomplete data management.

Referential Actions: ON DELETE and ON UPDATE

The default behavior when a parent row is deleted or its primary key is updated is to block the operation if child rows exist. This is often appropriate, but there are many real-world scenarios where a different automatic response is more useful. SQL allows you to declare a referential action that the database should take automatically. These actions are appended to the foreign key definition using the ON DELETE and ON UPDATE clauses.

CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id)
    REFERENCES customers (customer_id)
    ON DELETE CASCADE
    ON UPDATE CASCADE

The four standard referential actions are:

  • CASCADE. When the parent row is deleted, all matching child rows are automatically deleted as well. When the parent's primary key is updated, the foreign key in all matching child rows is automatically updated to the new value. CASCADE is useful when child records have no meaning without their parent — for example, deleting an invoice should probably also delete all its invoice_line_items. It can, however, trigger large cascading deletes across many rows and even chain through multiple levels of foreign keys, so it must be used thoughtfully.
  • SET NULL. When the parent row is deleted or updated, the foreign key column in the matching child rows is set to NULL. This is appropriate when the relationship is optional — for instance, if an employee's department is dissolved, the employee record might set department_id = NULL rather than being deleted. The foreign key column must be defined to allow NULL values for this action to work.
  • RESTRICT / NO ACTION. These prevent the delete or update on the parent row entirely if matching child rows exist, raising an error instead. The distinction between RESTRICT and NO ACTION is subtle and database-specific: in most systems, both produce the same immediate error, but NO ACTION can be deferred in databases that support deferred constraint checking (meaning the check happens at the end of a transaction rather than immediately). When neither action clause is specified, the default behavior is equivalent to RESTRICT or NO ACTION.
  • SET DEFAULT. When the parent row is deleted or updated, the foreign key column in the child rows is set to the column's declared default value. This requires that the column has a meaningful default and, in strict implementations, that the default value itself is a valid key in the parent table. Support for SET DEFAULT varies by database system — PostgreSQL supports it, while MySQL/InnoDB does not.

These actions can be combined independently for delete and update events:

CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id)
    REFERENCES customers (customer_id)
    ON DELETE SET NULL
    ON UPDATE CASCADE

This would cascade key updates (keeping child rows synchronized if a customer's ID changes) while setting the foreign key to NULL if the customer record is deleted outright.

Foreign Keys and NULL Values

A NULL value stored in a foreign key column is a special case. By definition, NULL means "unknown" or "not applicable," and the database treats a NULL foreign key as meaning "this row has no parent at this time." Because there is no value to check, a NULL foreign key is not considered a referential integrity violation. The database will accept the row without checking the parent table.

  • NULL as an optional relationship. This behavior is intentional and useful. Consider an employees table with a manager_id foreign key referencing employees (employee_id) — a self-referential relationship. The CEO of a company has no manager, so their manager_id should be NULL. Requiring a non-NULL value for every employee's manager would make it impossible to store the top of the hierarchy.
  • Making a relationship mandatory. If every row in the child table must be associated with a parent, define the foreign key column with a NOT NULL constraint. This forces every inserted or updated row to supply a valid foreign key value, and in combination with the foreign key constraint, ensures both that a value is present and that it exists in the parent table.
  • Flexibility through optional associations. Allowing NULLs in foreign key columns models scenarios where an association is possible but not required. An orders table might have a promo_code_id foreign key referencing a promo_codes table. Most orders may have no promotion applied, making NULL the normal case for that column, while the foreign key constraint still ensures that when a promo code ID is entered, it corresponds to a real promotion record.
-- Mandatory relationship: every order must have a customer
ALTER TABLE orders
    MODIFY customer_id INT NOT NULL;

-- Optional relationship: an order may or may not have a promo code
ALTER TABLE orders
    ADD COLUMN promo_code_id INT NULL,
    ADD CONSTRAINT fk_orders_promo
        FOREIGN KEY (promo_code_id)
        REFERENCES promo_codes (promo_code_id)
        ON DELETE SET NULL;

Foreign Keys vs. Primary Keys: Roles in Relationships

Primary keys and foreign keys serve complementary but distinct roles. A primary key identifies a row uniquely within its own table. A foreign key references a primary key in another table, establishing a directional link between the two. Several important distinctions emerge from these roles:

  • One primary key, many foreign keys. Every table can have at most one primary key (though that key may be composite). The same table can, however, carry any number of foreign keys, each pointing to a different parent table. An orders table might simultaneously have foreign keys referencing customers, products, sales_reps, and shipping_addresses. Each foreign key formalizes a separate relationship with a separate parent.
  • Foreign keys as the engine of JOIN operations. When you write a JOIN query, you are typically matching a foreign key column in the child table against the primary key column in the parent table. The foreign key constraint does not make JOIN queries syntactically mandatory — you could join on any column — but it documents and enforces the intended join relationship. Query optimizers in modern database engines also use foreign key metadata to make smarter execution plan decisions.
-- Joining orders to customers using the foreign key relationship
SELECT
    o.order_id,
    o.order_date,
    c.full_name,
    c.email
FROM orders o
JOIN customers c
    ON o.customer_id = c.customer_id
WHERE o.order_date >= '2024-01-01';
  • Formalizing the ER model in SQL. When database designers draw an entity-relationship (ER) diagram, they describe entities (customers, products, orders) and the relationships among them (a customer places orders, an order contains products). Primary keys represent the entity identifiers in that diagram. Foreign keys are the SQL implementation of the relationship lines. Together, the two constraint types translate an abstract conceptual model into a concrete, enforced database schema. This alignment between the ER model and the physical schema is what makes relational databases predictable, self-documenting, and auditable.

The practical consequence of understanding both constraint types together is that you can read a schema's table definitions and immediately understand the data model it encodes: which tables are parents, which are children, which relationships are mandatory, which are optional, and what happens when data is removed. This transparency is a hallmark of well-designed relational databases.
