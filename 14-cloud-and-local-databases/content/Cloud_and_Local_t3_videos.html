Introduction

A managed cloud database service is a database that runs on a provider's infrastructure, where the provider handles most of the underlying work: provisioning servers, installing and patching the database engine, taking backups, and keeping replicas available. You still design schemas, write queries, tune indexes, and control access, but you no longer rack hardware or babysit an operating system. The three services named in this topic — Amazon RDS, Azure SQL Database, and Google Cloud SQL — are the flagship relational offerings of the three largest public cloud providers, and they share far more in common than their marketing names suggest.

This matters in COP4708 because the choice between a locally hosted database and a cloud-based one changes how you budget, how you scale, who is responsible when something breaks, and how clients reach the database over a network. Managed services shift costs from large up-front purchases to recurring usage charges, replace manual capacity planning with resizing and read replicas, and divide administrative duties between you and the provider under a shared responsibility model. Understanding where that dividing line falls is the practical skill this topic builds.

As you watch the videos below, listen for a few recurring ideas: which tasks the provider automates versus which remain yours; how backups, replication, and high availability are described; how elasticity and pay-as-you-go pricing are framed; and how applications connect to a cloud database through endpoints, networking rules, and credentials. Also note that the videos come from IBM and AWS, so vendor terminology will appear — try to map each vendor-specific term back to the general concept it represents, since the same concept exists under a different name on Azure and Google Cloud.

How These Videos Support the Learning Outcomes

Together these videos build the cloud side of the comparison the module asks you to make.
