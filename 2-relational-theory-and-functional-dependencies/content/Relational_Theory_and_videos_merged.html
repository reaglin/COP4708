Mathematical Foundations of Relational Theory

Introduction

Before you can reason about keys, functional dependencies, or normalization, you need a precise vocabulary for what a relation actually is. In relational theory, a relation is not simply a table on a screen — it is a mathematical object defined in terms of sets. A domain is the set of permitted values for an attribute, a tuple is an ordered list of values drawn from those domains, and a relation is a subset of the Cartesian product of the domains involved. Attributes give each position in the tuple a name and a semantic meaning, which is what lets us talk about columns by label rather than by position.

This mathematical grounding matters for the rest of the course because every later result — Armstrong's Axioms, attribute closure, candidate key identification, and the normal forms — is stated and proved in set-theoretic language. If you are comfortable with the ideas of set membership, Cartesian products, n-ary relations, and the distinction between a relation schema (the structure) and a relation instance (the current set of tuples), the formal parts of Module 2 will read as straightforward consequences rather than as arbitrary rules.

As you watch the videos below, keep a running glossary. For each term — domain, tuple, attribute, degree, cardinality, relation, relation schema — write down both the formal definition and the everyday table-based analogy. Notice especially where the practical database vocabulary (table, row, column) lines up with the mathematical vocabulary (relation, tuple, attribute), and where the two differ: tables may tolerate duplicate rows and rely on column order, while a mathematical relation is a set and therefore cannot.

Relations, Tuples, and Attributes

Introduction

The relational model describes data using a small number of precisely defined pieces. A relation is a set of tuples over a fixed set of attributes; informally, we draw it as a table, where each row is a tuple and each column is an attribute. Each attribute is associated with a domain — the set of permitted values for that column — and the relation schema names the relation and lists its attributes (and their domains). Because a relation is formally a set, there are no duplicate tuples and no inherent ordering of rows; column order is likewise unimportant once attributes are named.

These definitions matter for everything else in this module. Functional dependencies, candidate keys, attribute closure, and normalization are all stated in terms of attributes and the tuples of a relation, so being comfortable moving between the picture (a table) and the formalism (a set of tuples over attributes with domains) is the prerequisite for the rest of the course.

The videos below approach these ideas from a practical, industry-facing angle. As you watch, deliberately translate the vocabulary you hear — table, row, column, field, data type, key — into the formal terms relation, tuple, attribute, domain, and relation schema. Note where the informal presentation differs from the strict set-theoretic definition (for example, treating tables as ordered lists of rows), and be ready to state the formal version yourself.

Introduction to Functional Dependencies

Introduction

A functional dependency (FD) is a statement about a relation that says: if two tuples agree on the values of one set of attributes, they must also agree on the values of another set. We write this as X -> Y, read "X functionally determines Y" or "Y is functionally dependent on X." The left-hand side X is called the determinant. For example, in a relation about students, StudentID -> Name asserts that a given StudentID value can never be paired with two different names.

FDs are not facts you discover by staring at one snapshot of data; they are constraints that come from the meaning of the data in the real world the database models. That is why the context matters: an FD is always stated over the attributes of a particular relation schema. This connects directly back to the formal relational vocabulary from earlier in the module — domains, attributes, tuples, and schemas — because an FD is a rule about which tuples are legal in a relation.

As you work through this topic, pay attention to three things. First, the notation and how to read it aloud correctly. Second, the distinction between trivial FDs (where the right-hand side is contained in the left-hand side, such as {A, B} -> A, and which hold automatically) and non-trivial FDs, which carry real information. Third, why any of this matters: FDs are the foundation for keys, for Armstrong's Axioms, for attribute closure, and ultimately for normalization and the elimination of redundancy and update anomalies. The videos below approach these ideas at different levels of depth, so watch them in order and treat the later ones as a preview of where FDs lead.

Types and Properties of Functional Dependencies

Introduction

A functional dependency (written X -> Y) says that the values of attribute set X determine the values of attribute set Y: any two tuples that agree on X must agree on Y. Once you can state dependencies formally, you can classify them. A dependency is trivial when the right side is already contained in the left side (for example, {StudentID, Name} -> Name), and non-trivial when it tells you something new about the data. Trivial dependencies always hold by definition; non-trivial ones encode real business rules and are the ones that drive key discovery and normalization.

Armstrong's Axioms give you a sound and complete set of inference rules for reasoning about dependencies: reflexivity (if Y is a subset of X, then X -> Y), augmentation (if X -> Y, then XZ -> YZ), and transitivity (if X -> Y and Y -> Z, then X -> Z). From these three, the commonly used derived rules follow — union, decomposition, and pseudotransitivity. Applying them repeatedly lets you compute the closure of an attribute set (X+), which is the practical tool for testing whether a dependency is implied, identifying candidate keys, checking whether two FD sets are equivalent, and reducing an FD set to a canonical (irreducible) cover.

As you watch the videos below, keep three questions in mind. First, for every example dependency, decide for yourself whether it is trivial or non-trivial before the narrator says so. Second, when a new dependency is derived, name the axiom or derived rule that justifies each step. Third, notice how closure computation is really just Armstrong's Axioms applied mechanically — that connection is what makes the later topics of candidate keys and normalization manageable.

Functional Dependencies and Database Design

Introduction

Functional dependencies are more than an abstract piece of relational theory — they are the blueprint you use when deciding what tables a database should have and which attributes belong in each one. A dependency such as StudentID -> Advisor is a statement about the real world: it says that knowing a student determines exactly one advisor. Once you write down the dependencies that hold over your data, the structure of a good schema follows from them in a fairly mechanical way.

When dependencies are ignored, the cost shows up as redundancy and as insertion, deletion, and update anomalies: the same fact stored in many rows, facts that cannot be recorded because no complete row exists yet, and facts that vanish when an unrelated row is deleted. Normalization is the systematic response. Each normal form (2NF, 3NF, BCNF, and beyond) is defined in terms of functional dependencies and keys, and moving a schema into a higher normal form means decomposing relations so that every dependency has a key on its left side. Two properties constrain how you decompose: the decomposition must be lossless (joining the pieces back together recovers exactly the original relation, no spurious tuples) and ideally dependency preserving (every original dependency can still be enforced on a single fragment without a join).

While watching these videos, keep three questions in mind. First, which attribute closures and candidate keys are being computed, and how are they used to justify a split? Second, what specific anomaly does each decomposition eliminate? Third, note carefully the trade-off the first video highlights: BCNF is the stricter condition, but it does not always allow a dependency-preserving decomposition, which is why 3NF remains a practical target in real designs.
