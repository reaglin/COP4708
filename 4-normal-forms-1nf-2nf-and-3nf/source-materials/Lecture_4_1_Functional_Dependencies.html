Functional Dependency in Relational Databases

Functional dependency is a fundamental concept in relational database theory that describes the relationship between attributes in a relation (or table). It states that if we know the value of one attribute (or set of attributes), we can uniquely determine the value of another attribute (or set of attributes).

Example: Consider a relation named Employee with attributes EmployeeID, Name, Department, and Salary. A functional dependency might exist between:

  • EmployeeID and Name: This means that if you know the EmployeeID, you can uniquely determine the Name of the employee.
  • Department and Salary: This might imply that employees in the same department have the same salary (although this might not be true in real-world scenarios).

Notation: Functional dependencies are often represented using an arrow notation. For instance, the above dependencies would be written as:

  • EmployeeID → Name
  • Department → Salary

Key Points:

  • Trivial Dependency: A dependency where the right-hand side is a subset of the left-hand side is called a trivial dependency. For example, EmployeeID → EmployeeID.
  • Non-Trivial Dependency: A dependency that is not trivial is called a non-trivial dependency.
  • Superkey: A set of attributes that functionally determines all attributes in a relation is called a superkey.
  • Candidate Key: A minimal superkey (i.e., a superkey that cannot be reduced further without losing its property) is called a candidate key.

Importance of Functional Dependencies: Functional dependencies are crucial for:

  • Normalization: Ensuring that the database is in a normalized form, which helps to reduce redundancy and improve data integrity.
  • Query Optimization: The database system can use functional dependencies to optimize query execution plans.
  • Database Design: Understanding functional dependencies helps in designing efficient and maintainable database schemas.

By understanding functional dependencies, database designers can create well-structured and efficient databases that meet the specific requirements of an application.

Example of a non-trivial dependency:

Consider a table called Orders with the following attributes:

  • OrderID (primary key)
  • CustomerID
  • OrderDate
  • ShippingAddress

A non-trivial dependency in this table might be:

  • CustomerID → ShippingAddress

This means that if you know the CustomerID, you can uniquely determine the ShippingAddress associated with that customer. This is a non-trivial dependency because ShippingAddress is not a subset of CustomerID.

In other words, knowing the customer's ID tells you something new about their shipping address.

Example of a superkey:

Consider a table called Orders with the following attributes:

  • OrderID (primary key)
  • CustomerID
  • OrderDate
  • ShippingAddress

A superkey for this table could be:

  • OrderID, CustomerID, OrderDate

This combination of attributes uniquely identifies each row in the table. Even though OrderID alone is sufficient to uniquely identify a row (as it's the primary key), adding CustomerID and OrderDate to the combination still forms a superkey.

A superkey doesn't have to be minimal (i.e., it can contain redundant attributes). In this case, OrderID is redundant because it's already part of the primary key. However, the combination of all three attributes still uniquely identifies each row.
