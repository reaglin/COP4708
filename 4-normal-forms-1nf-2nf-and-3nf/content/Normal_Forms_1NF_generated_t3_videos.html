Introduction

Second Normal Form (2NF) is the next step after 1NF in the normalization process. Once a table is in 1NF — every attribute holds a single atomic value and a primary key has been designated — the question becomes whether every non-key attribute actually depends on the whole primary key. When a table has a composite primary key (a key made of two or more attributes), it is possible for some non-key attribute to be determined by only part of that key. That situation is called a partial dependency, and 2NF exists to remove it: a table is in 2NF if it is in 1NF and every non-key attribute is fully functionally dependent on the entire primary key.

This matters because partial dependencies cause the same anomalies you studied earlier in the module. If a product's name is stored in an order-line table keyed on (OrderID, ProductID), the product name repeats on every line, must be updated in many rows at once, and cannot be recorded at all until some order references it. Decomposing the table — pulling the partially dependent attributes out into their own table keyed on the determinant — removes the redundancy without losing information, because the original table can be reconstructed by joining.

As you watch the videos below, keep three things in view. First, notice how each presenter writes out the functional dependencies before judging the table; the dependencies, not intuition, decide the answer. Second, watch for the shortcut rule that a table with a single-attribute primary key and no repeating groups is automatically in 2NF, and make sure you understand why. Third, follow the decomposition carefully: which attributes move, what becomes the key of the new table, and what stays behind as a foreign key.
