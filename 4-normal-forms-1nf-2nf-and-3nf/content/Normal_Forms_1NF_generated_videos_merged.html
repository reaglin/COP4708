Introduction to Normalization

Introduction

Normalization is the systematic process of organizing the tables and columns of a relational database so that each fact is stored in exactly one place. When a design stores the same fact repeatedly — a customer's address repeated on every order row, for example — the database becomes vulnerable to inconsistency: one copy gets updated and the others do not. Normalization attacks this problem at the structural level by examining how attributes depend on keys and splitting tables until each table describes one kind of thing.

In this module you will work through the first three normal forms in detail, so this introductory topic sets up the vocabulary and the motivation you will need. Pay particular attention to the three classic anomalies — insertion, update, and deletion — because they are the practical symptoms that tell you a table is badly designed. Equally important is the idea of a functional dependency: the statement that one set of attributes determines another. Every rule you will learn for 1NF, 2NF, and 3NF is ultimately a statement about which dependencies are allowed to live in a table.

As you watch the videos below, look for three things: concrete examples of redundancy and the trouble it causes, the role of keys in deciding where an attribute belongs, and the reasoning behind each normal form rather than just its definition. The third video deliberately covers denormalization — the deliberate reintroduction of redundancy — so that you understand normalization as a design judgment with trade-offs, not a rule to be applied blindly.

First Normal Form (1NF)

Introduction

First Normal Form is the entry point to database normalization. A table is in 1NF when every column holds a single, indivisible (atomic) value, when there are no repeating groups of columns such as Phone1, Phone2, Phone3, and when each row can be uniquely identified by a primary key. These rules sound simple, but applying them to a messy real-world spreadsheet-style table is where most of the learning happens.

In this course, 1NF matters because every later step depends on it. You cannot meaningfully look for partial dependencies (2NF) or transitive dependencies (3NF) until the data is in a flat, atomic, key-identified structure. The anomalies you studied earlier in this module - insertion, update, and deletion problems - are often made much worse by comma-separated lists and repeated column groups, so putting a table into 1NF is usually the first concrete repair you perform.

As you watch, keep three questions in mind. First, what exactly counts as atomic, and where do people disagree about it? Second, when a repeating group is removed, how many rows does the table gain, and what does that do to the key? Third, what becomes the primary key after the transformation - a single column, or a composite of two or more? Try to pause each video at the "before" table and sketch your own "after" table before the presenter reveals theirs.

Second Normal Form (2NF)

Introduction

Second Normal Form (2NF) is the next step after 1NF in the normalization process. Once a table is in 1NF — every attribute holds a single atomic value and a primary key has been designated — the question becomes whether every non-key attribute actually depends on the whole primary key. When a table has a composite primary key (a key made of two or more attributes), it is possible for some non-key attribute to be determined by only part of that key. That situation is called a partial dependency, and 2NF exists to remove it: a table is in 2NF if it is in 1NF and every non-key attribute is fully functionally dependent on the entire primary key.

This matters because partial dependencies cause the same anomalies you studied earlier in the module. If a product's name is stored in an order-line table keyed on (OrderID, ProductID), the product name repeats on every line, must be updated in many rows at once, and cannot be recorded at all until some order references it. Decomposing the table — pulling the partially dependent attributes out into their own table keyed on the determinant — removes the redundancy without losing information, because the original table can be reconstructed by joining.

As you watch the videos below, keep three things in view. First, notice how each presenter writes out the functional dependencies before judging the table; the dependencies, not intuition, decide the answer. Second, watch for the shortcut rule that a table with a single-attribute primary key and no repeating groups is automatically in 2NF, and make sure you understand why. Third, follow the decomposition carefully: which attributes move, what becomes the key of the new table, and what stays behind as a foreign key.

Third Normal Form (3NF)

Introduction

Third Normal Form (3NF) is the point in the normalization process where you remove dependencies that travel through an intermediate attribute. A transitive dependency occurs when a non-key attribute determines another non-key attribute, so the second attribute depends on the primary key only indirectly. A classic pattern looks like this: in an Employee table keyed by EmployeeID, the DepartmentID determines DepartmentName, so DepartmentName depends on EmployeeID only through DepartmentID. The fix is to split the dependent attributes into their own table and keep the determinant as a foreign key.

In this course, 3NF matters because it is the practical stopping point for most production schemas. Once a table is in 2NF, leftover transitive dependencies are what still cause redundant storage and the insertion, update, and deletion anomalies you studied earlier in the module. Decomposing to 3NF keeps each fact recorded in exactly one place, which makes updates safe and keeps referential integrity meaningful.

As you watch the videos below, pay attention to three things: how each presenter identifies the determinant of a suspect attribute, how the original table is split (which attribute stays behind as a foreign key), and how the resulting tables are checked against the 1NF and 2NF rules you already know. Try pausing before each worked solution and attempting the decomposition yourself, then compare your answer to the presenter's.

Applying Normal Forms: End-to-End Practice

Introduction

Up to this point in the module you have studied each normal form on its own: atomicity and repeating groups for 1NF, partial dependencies for 2NF, and transitive dependencies for 3NF. This topic puts those pieces together into a single workflow. You start with a messy, unnormalized table — the kind that holds multiple values in one cell, repeats the same customer or product facts on many rows, and breaks when you try to insert, update, or delete a record — and you carry it step by step all the way to a set of 3NF tables.

The reason this end-to-end practice matters is that normalization in real design work is rarely one isolated decision. Each step changes the table you are working with, and the dependencies you must examine at step two are the ones left over after step one. Working through a full example also trains you to justify each decomposition: which functional dependency forced the split, which key the new table uses, and how the original data can still be reconstructed through foreign keys.

As you watch the videos below, keep a pencil moving. Write down the candidate keys at each stage, mark which attributes depend on only part of a composite key (partial dependency) and which depend on another non-key attribute (transitive dependency), and sketch the resulting tables yourself before the presenter reveals them. Afterwards, check your final schema against all three normal forms, table by table, the same way you would validate your own design in an assignment.
