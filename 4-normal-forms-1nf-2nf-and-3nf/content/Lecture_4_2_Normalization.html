Normalization in Relational Databases

Normalization is the process of organizing data in a database to minimize redundancy and ensure data integrity. It involves breaking down large tables into smaller, more focused ones that are related through primary and foreign keys.  

Reasons for Normalization

  • Data Integrity: Prevents data inconsistencies and anomalies that can occur when data is duplicated.
  • Data Redundancy: Reduces storage requirements and improves query performance by eliminating redundant data.
  • Data Consistency: Ensures that data is consistent across the database.
  • Maintainability: Makes the database easier to maintain and update.

Anomalies and Their Fixes

1. Insertion Anomalies:

  • Example: A new employee is hired but cannot be added to the database because their department doesn't exist yet.
  • Fix: Create separate tables for employees and departments, linking them with a foreign key.

2. Deletion Anomalies:

  • Example: Deleting a department accidentally deletes all associated employees.
  • Fix: Separate tables for employees and departments, allowing for the deletion of a department without affecting the employees.

3. Update Anomalies:

  • Example: Updating a department name requires updating it in multiple records where that department is referenced.
  • Fix: Store department information in a separate table and reference it using a foreign key.

Normal Forms

  • First Normal Form (1NF): Each attribute in a table should be atomic (indivisible).
  • Second Normal Form (2NF): A table is in 2NF if it is in 1NF and no non-key attribute is dependent on a part of the primary key.
  • Third Normal Form (3NF): A table is in 3NF if it is in 2NF and there are no transitive dependencies between non-key attributes.

Example:

Consider a table called Orders with attributes: OrderID, CustomerID, CustomerName, CustomerAddress, Product, Price.

  • Unnormalized: This table is not in 1NF because CustomerAddress is a repeating group within a row.
  • 1NF: Separate CustomerAddress into a separate table CustomerAddresses, linking it to Orders using a foreign key.
  • 2NF: If CustomerID is the primary key, CustomerName and CustomerAddress are partially dependent on CustomerID. Move these attributes to the CustomerAddresses table.
  • 3NF: If Price depends on Product, and Product is not part of the primary key, this is a transitive dependency. Create a separate table Products to store Product and Price.

By normalizing the database, we ensure that data is stored efficiently, consistently, and without anomalies.
