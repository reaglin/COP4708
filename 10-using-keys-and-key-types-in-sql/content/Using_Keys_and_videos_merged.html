Introduction to Keys in SQL

Introduction

A key is a column, or a combination of columns, whose values let you identify rows in a table or connect rows across tables. Without keys, a relational database is just a collection of lists: you cannot reliably say which row you mean, you cannot stop duplicates from creeping in, and you cannot tell which order belongs to which customer. Keys are what turn separate tables into a connected, trustworthy model of your data.

In this module you will work with several kinds of keys — primary, foreign, candidate, composite, and surrogate — and you will declare them in SQL as constraints using CREATE TABLE and ALTER TABLE. This first topic lays the groundwork: what a key is, why keys matter for organizing and identifying data, how they protect data integrity, and how the database engine enforces them automatically once you declare them.

As you watch the videos below, keep three questions in mind. First, what makes a set of column values suitable as an identifier (uniqueness, non-null, stability)? Second, how does a foreign key in one table point back to a key in another, and what happens when the referenced row changes or is deleted? Third, notice the difference between a key as a design idea and a key as a constraint you actually write in SQL — that distinction carries through the rest of the module.

Primary Keys

Introduction

A primary key is the column — or combination of columns — that uniquely identifies every row in a table. Because no two rows may share the same primary key value, and because a primary key column cannot be left empty (NULL), the primary key is the database's guarantee that each record can be found, updated, or referenced without ambiguity. In SQL you declare this guarantee as a constraint, either while creating the table or later with an ALTER TABLE statement, and the database engine enforces it on every insert and update from that point forward.

Primary keys matter in this course for two reasons. First, they are the foundation of data integrity: without one, duplicate or near-duplicate rows creep in and queries return unreliable results. Second, they are the anchor point for relationships — a foreign key in one table points at the primary key of another, so every topic later in this module depends on understanding this one. Choosing a key well also has practical consequences for performance and for how painful future schema changes will be.

As you watch the videos below, pay attention to three things: the exact SQL syntax used to declare, add, and drop the constraint; what the database does when you try to insert a duplicate or NULL value; and the reasoning behind choosing one column (or set of columns) over another as the key. Note also that syntax and behavior differ slightly between database systems, so compare what you see against the system you are using in this course.

Foreign Keys and Referential Integrity

Introduction

A foreign key is a column (or set of columns) in one table whose values must match an existing primary key or unique key value in another table. That simple rule is what turns a collection of separate tables into a connected relational database: an order row can point to the customer who placed it, an enrollment row can point to both a student and a course. Without foreign keys, nothing stops your database from storing an order for a customer who does not exist.

The rule that these references must always point to something real is called referential integrity, and the database enforces it for you through FOREIGN KEY constraints. In this topic you will see how to declare those constraints in CREATE TABLE and ALTER TABLE statements, how NULL values are handled in a foreign key column (a NULL means "no relationship yet," not a broken one), and how referential actions such as ON DELETE CASCADE, ON DELETE SET NULL, and ON UPDATE CASCADE tell the database what to do when a referenced parent row is deleted or changed.

As you watch, keep three questions in mind. First, which table is the parent (the one holding the referenced key) and which is the child (the one holding the foreign key)? Second, what exact SQL syntax creates the constraint, and what error does the database raise when the constraint is violated? Third, what happens to the child rows when a parent row is deleted — and why choosing the right referential action matters more than it first appears. Note that syntax and default behavior can vary slightly between database systems, so compare what you see in the videos with the syntax used in our course environment.

Candidate Keys

Introduction

A candidate key is any column, or combination of columns, that could legitimately serve as the primary key of a table. To qualify, the column set must satisfy two properties: uniqueness, meaning no two rows can ever share the same value for that set, and irreducibility (minimality), meaning you cannot remove any column from the set and still guarantee uniqueness. A table often has more than one candidate key; the designer selects one to be the primary key, and the others become alternate keys.

This distinction matters in COP4708 because key selection drives much of your schema design. The primary key you choose determines how other tables reference this one through foreign keys, while the candidate keys you do not choose still need protection so that duplicate values never slip in. In SQL, that protection comes from UNIQUE constraints, which enforce the uniqueness property of alternate keys without making them the table's identifying key.

As you watch the videos below, pay close attention to the relationship between super keys, candidate keys, and primary keys: every candidate key is a super key, but not every super key is minimal enough to be a candidate key. Try to follow the reasoning the presenters use when they test a column combination for uniqueness and then strip away unnecessary columns. Then practice that same reasoning on a sample table of your own before moving on to writing the SQL constraints.

Composite Keys

Introduction

A composite key is a key made up of two or more columns that, taken together, uniquely identify a row. No single column in the combination is unique on its own, but the combination is. Composite keys show up constantly in real schemas: in bridge (junction) tables that resolve many-to-many relationships, in line-item tables keyed by order number plus line number, and in any table where the natural identifier is genuinely multi-part.

In this module you are learning to tell key types apart and to write the constraints that enforce them. Composite keys are where that gets interesting, because the syntax changes: you can no longer declare the key inline next to a single column, so you use a table-level PRIMARY KEY (col1, col2) or UNIQUE (col1, col2) clause, or add it later with ALTER TABLE ... ADD CONSTRAINT. Foreign keys that point at a composite key must also list the matching columns in the same order.

As you watch, pay attention to three things: the exact placement and syntax of the table-level constraint, how the videos justify choosing a multi-column natural key instead of a single surrogate ID, and how a child table references a composite parent key. Also note the trade-offs mentioned — composite keys can enforce meaningful business rules, but they make joins wordier and propagate more columns into every referencing table.

Enforcing Key Constraints for Data Integrity

Introduction

Keys are only useful if the database actually enforces them. In this topic we move from identifying keys conceptually to declaring them as constraints that the database management system checks on every insert, update, and delete. PRIMARY KEY, FOREIGN KEY, and UNIQUE constraints are the mechanisms that turn a design decision on paper into a guarantee the data cannot violate.

You will look at why constraints matter for data integrity, how to declare them in CREATE TABLE and later add them with ALTER TABLE, how foreign keys protect referential integrity between related tables, and how UNIQUE enforces candidate keys that were not chosen as the primary key. You will also weigh composite natural keys against surrogate keys, and learn the practical side of constraint management: naming, adding, disabling, and dropping constraints without breaking existing data.

As you watch, pay attention to three things: the exact SQL syntax used (especially the CONSTRAINT name clause), what error the database raises when a constraint is violated, and what happens when you try to add a constraint to a table that already contains rows that would violate it. Those details are what separate working schemas from fragile ones.
