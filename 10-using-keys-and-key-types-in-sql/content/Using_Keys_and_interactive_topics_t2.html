Primary Keys

▶

A primary key is one of the most fundamental concepts in relational database design. At its core, a primary key is a column — or a combination of columns — in a database table whose values uniquely identify every single row in that table. Think of it like a social security number for each record: no two rows can share the same primary key value, and every row must have one. Without primary keys, a relational database would quickly become a chaotic collection of data with no reliable way to pinpoint, relate, or protect individual records.

To fully appreciate why primary keys matter and how to use them correctly, we need to examine their defining characteristics, their role in database architecture, and the practical SQL syntax used to create, modify, and remove them.

What Is a Primary Key?

A primary key is defined by three inviolable rules that together guarantee every record in a table can always be found and distinguished from every other record.

Uniqueness: Every value stored in a primary key column must be unique across all rows in the table. If a table tracks customers and uses customer_id as its primary key, then no two customers can share the same customer_id. The moment you attempt to insert a second row with an already-existing key value, the database engine will reject the operation with a constraint violation error. This is not something the developer has to code manually — the database enforces it automatically and unconditionally.

Non-nullability: A primary key column cannot contain NULL values. NULL in SQL represents the absence of a value — it means "unknown" or "not applicable." If a primary key were allowed to be NULL, the database would have rows it cannot reliably identify. Imagine trying to look up a customer whose ID is unknown — it simply doesn't work. The NOT NULL constraint is implicitly applied to every primary key column, even if you don't write it explicitly in your CREATE TABLE statement.

Singularity per table: Each table can have only one primary key. However, that single primary key may be composite — meaning it spans two or more columns. For example, an order-items table might use both order_id and product_id together as its primary key, since neither column alone uniquely identifies a row, but the combination does. The important distinction is that the table still has exactly one primary key constraint, even though that constraint encompasses multiple columns.

Consider a simple customers table. Without a primary key, multiple rows with identical names and addresses could exist with no way to tell them apart:

-- Without a primary key, duplicates can slip in:
INSERT INTO customers (name, email) VALUES ('Alice Smith', 'alice@example.com');
INSERT INTO customers (name, email) VALUES ('Alice Smith', 'alice@example.com'); -- exact duplicate!

Both inserts would succeed, leaving you with two indistinguishable records. A primary key eliminates this problem entirely.

Why Primary Keys Matter

Primary keys are not merely a formality — they serve several critical functions that underpin the entire relational model.

Preventing duplicate records: By enforcing uniqueness at the database engine level, primary keys act as the last line of defense against duplicate data. Even if application code has a bug that tries to insert the same record twice, the database will refuse the second insertion. This is far more reliable than relying solely on application-level validation, which can be bypassed, forgotten, or circumvented in multi-user environments.

Anchoring foreign key relationships: In a relational database, tables are connected to one another through foreign keys. A foreign key in one table (the child) references the primary key of another table (the parent). For example, an orders table might have a customer_id column that references the customer_id primary key in the customers table. This linkage is what makes it possible to join tables meaningfully and ensures referential integrity — you cannot have an order belonging to a customer who doesn't exist. The primary key is the anchor point that makes all of this possible.

-- The primary key in the parent table:
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name        VARCHAR(100)
);

-- The foreign key in the child table references it:
CREATE TABLE orders (
    order_id    INT PRIMARY KEY,
    customer_id INT,
    order_date  DATE,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

Enabling efficient indexing: When you define a primary key, virtually every major database system (MySQL, PostgreSQL, SQL Server, Oracle, SQLite) automatically creates a unique index on that column or set of columns. An index is a behind-the-scenes data structure — often a B-tree — that allows the database engine to locate rows extremely quickly without scanning every row in the table. When you query WHERE customer_id = 42, the index lets the engine jump directly to that record in a tiny fraction of the time it would take to read the entire table. This becomes especially important as tables grow to millions of rows.

Defining a Primary Key at Table Creation

The most common place to define a primary key is inside the CREATE TABLE statement. There are two syntactically valid approaches.

Inline (column-level) definition: For a single-column primary key, you can place the PRIMARY KEY keyword directly after the column's data type in its definition line. This is concise and easy to read at a glance:

CREATE TABLE products (
    product_id   INT          PRIMARY KEY,
    product_name VARCHAR(150) NOT NULL,
    price        DECIMAL(10, 2)
);

Here, product_id is declared as the primary key inline. The database will automatically enforce uniqueness and non-nullability on this column and will create a unique index for it.

Table-level (out-of-line) constraint definition: Alternatively, you can declare the primary key as a separate constraint clause at the end of the column list, after all column definitions. This style is required for composite (multi-column) primary keys and is often preferred for clarity in complex tables:

CREATE TABLE order_items (
    order_id   INT           NOT NULL,
    product_id INT           NOT NULL,
    quantity   INT           NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL,
    CONSTRAINT pk_order_items PRIMARY KEY (order_id, product_id)
);

In this example, neither order_id nor product_id is unique on its own — a single order can contain many products, and a single product can appear in many orders — but the combination of the two is unique for each line item. The CONSTRAINT pk_order_items part gives the primary key constraint an explicit name, which is a best practice for maintainability.

The table below summarizes the two approaches:

Approach Syntax Location Supports Composite Keys? Best Used When
Inline (column-level) After the column's data type No — single column only Simple, single-column primary keys
Table-level constraint After all column definitions Yes — one or more columns Composite keys or when naming the constraint explicitly

Adding a Primary Key to an Existing Table

Sometimes a table is created without a primary key, or you inherit a legacy database that lacks proper constraints. In these cases, you can add a primary key after the fact using ALTER TABLE.

However, before you attempt this, you must ensure two preconditions are met in the target column:

  • The column must contain no NULL values. If any row has a NULL in that column, the database will reject the constraint addition.
  • The column must contain no duplicate values. If two rows share the same value in the candidate column, the uniqueness requirement cannot be satisfied.

You can check for these issues before altering the table:

-- Check for NULLs:
SELECT COUNT(*) FROM employees WHERE employee_id IS NULL;

-- Check for duplicates:
SELECT employee_id, COUNT(*)
FROM employees
GROUP BY employee_id
HAVING COUNT(*) > 1;

Once you've confirmed the column is clean, add the primary key constraint:

ALTER TABLE employees
ADD CONSTRAINT pk_employees PRIMARY KEY (employee_id);

Giving the constraint an explicit name (pk_employees) is strongly recommended. Named constraints are much easier to reference later when you need to drop or inspect them. Without a name, the database auto-generates an internal name that varies by platform and can be difficult to discover.

Enforcing the Primary Key Constraint

One of the greatest advantages of primary keys is that their enforcement is entirely automatic and happens at the database engine level — no application code required. Once the constraint is in place, the database police every write operation against the table.

INSERT violations: If you attempt to insert a row whose primary key value already exists in the table, the database immediately aborts the insert and returns an error. The transaction (if any) can be rolled back, leaving the data in a consistent state:

-- Suppose product_id 101 already exists:
INSERT INTO products (product_id, product_name, price)
VALUES (101, 'Widget Pro', 29.99);

-- Error: Duplicate entry '101' for key 'PRIMARY'

UPDATE violations: The constraint also guards against updates that would introduce a duplicate key or set the key to NULL:

-- Attempt to change product_id to a value that already exists:
UPDATE products SET product_id = 101 WHERE product_id = 205;
-- Error: Duplicate entry '101' for key 'PRIMARY'

-- Attempt to set the primary key to NULL:
UPDATE products SET product_id = NULL WHERE product_id = 205;
-- Error: Column 'product_id' cannot be null

This blanket protection means that data integrity is maintained even if multiple applications, scripts, or users are writing to the database simultaneously. There is no race condition where two inserts could both "check" and both "pass" before either writes — the database engine handles this atomically.

Dropping a Primary Key Constraint

There are legitimate reasons to drop a primary key: restructuring a schema, changing which column serves as the key, or migrating data. The syntax differs slightly between database systems:

-- MySQL:
ALTER TABLE products DROP PRIMARY KEY;

-- PostgreSQL and SQL Server (using the constraint name):
ALTER TABLE products DROP CONSTRAINT pk_products;

Before dropping a primary key, you must address any foreign key constraints in other tables that reference it. A foreign key in a child table cannot reference a primary key that no longer exists. If you try to drop the primary key while foreign keys reference it, the database will refuse:

-- This will fail if orders.product_id references products.product_id:
ALTER TABLE products DROP PRIMARY KEY;
-- Error: Cannot drop index 'PRIMARY': needed in a foreign key constraint

You must first drop (or temporarily disable) the foreign key constraint in the child table, then drop the primary key, make your changes, and re-establish both constraints. After dropping the primary key constraint, the column's data remains intact — the rows are not deleted. However, uniqueness and non-null enforcement are no longer guaranteed going forward, and the automatic index may be removed, potentially degrading query performance.

Best Practices for Choosing a Primary Key

Selecting the right primary key is a design decision with long-term consequences. Here are the key principles to guide that decision:

  • Choose an immutable value. The ideal primary key value never changes over the lifetime of a record. If a primary key value changes, every foreign key referencing it must also be updated — a potentially expensive cascade operation across many tables. For example, using an employee's email address as a primary key is risky: people change email addresses. A surrogate integer ID that is assigned once and never changed is far safer.
  • Keep the data type small. Primary keys are indexed, and those indexes are also copied into every foreign key index in related tables. A 4-byte INT index is significantly more compact and faster than a 36-byte VARCHAR(36) UUID string. Smaller key types mean smaller indexes, less memory usage, and faster joins. Use INT or BIGINT for numeric keys where possible; if you need globally unique IDs (e.g., for distributed systems), consider storing UUIDs as binary values (BINARY(16)) rather than strings.
  • Avoid sensitive or personally identifiable information (PII). Using a Social Security Number, passport number, or national ID as a primary key exposes that sensitive data in every join, every log, every foreign key column, and potentially every API response. If that data is leaked or needs to be deleted under privacy regulations (like GDPR's "right to erasure"), having it baked into your referential integrity structure makes compliance extremely difficult. Use a meaningless surrogate key instead.
  • Prefer surrogate keys over natural keys in most cases. A natural key is a key derived from the real-world data itself (e.g., a product's ISBN, a country's ISO code). A surrogate key is an artificially generated identifier with no business meaning (e.g., an auto-incremented integer). Natural keys can seem appealing because they're already meaningful, but they often violate the immutability principle — business rules change, ISBNs get reassigned, and what seemed stable turns out not to be. Surrogate keys are almost always the safer long-term choice.

The following table summarizes common primary key candidates and their trade-offs:

Key Type Example Pros Cons
Auto-increment INT 1, 2, 3, ... Small, fast, simple, immutable Not globally unique across databases; predictable (security concern)
UUID (string) '550e8400-e29b...' Globally unique; safe for distributed systems Large (36 bytes as string); slower indexing; poor locality
Natural key ISBN, email, SSN Human-readable; already meaningful Can change; may be sensitive; often longer data types
Composite key (order_id, product_id) No extra column needed; reflects real-world uniqueness More complex joins; larger foreign key references
UUID (binary) BINARY(16) Globally unique; more compact than string UUID Not human-readable; requires conversion for display

Understanding primary keys deeply — not just how to write the syntax but why they work the way they do — is foundational to building databases that are correct, efficient, and maintainable. Every design decision downstream, from foreign keys to indexes to application queries, depends on the quality of your primary key choices.
