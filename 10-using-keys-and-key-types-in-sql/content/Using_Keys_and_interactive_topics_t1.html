Introduction to Keys in SQL

▶

At the heart of every well-designed relational database lies a deceptively simple idea: every piece of data must be reliably identifiable, reachable, and relatable to other data. Keys are the mechanism that makes this possible. A key, in the context of a relational database, is a column or set of columns whose values uniquely identify each row within a table, or whose values establish a meaningful link between rows in different tables. Without keys, a database is little more than a collection of loosely organized spreadsheets — data can be duplicated, relationships become ambiguous, and retrieval becomes slow and error-prone.

Understanding keys is not merely an academic exercise. Every practical task in SQL — from writing a precise JOIN to preventing a botched bulk update — depends on a sound grasp of how keys are defined, enforced, and used. This topic builds that foundation by examining what keys are, why they matter, how they protect data integrity, what varieties exist, and how SQL expresses them as formal constraints.

What Is a Key in a Relational Database?

A key is any column, or ordered combination of columns, whose values can be used to distinguish one row from every other row in the same table. This property is called uniqueness. Consider a table of employees:

employee_id first_name last_name department
1001AliceMarshEngineering
1002BobChenMarketing
1003AliceJordanEngineering

Notice that first_name alone cannot be a key — two employees share the name "Alice." The column employee_id, however, holds a distinct value for every row, making it a suitable key. This is the essence of uniqueness: no two rows may carry the same value (or the same combination of values, when multiple columns form the key) in the key column(s).

A key may be simple (a single column, like employee_id) or composite (two or more columns whose combined values are unique, even though the individual columns are not). For example, a course enrollment table might have neither student_id alone nor course_id alone as unique — a student can enroll in many courses, and a course can have many students — but the pair (student_id, course_id) uniquely identifies each enrollment record.

Keys are rooted in the formal relational model introduced by E. F. Codd in 1970. In that model, a relation (what SQL calls a table) is defined as a set of tuples (rows), and sets by definition contain no duplicates. Keys are the practical instrument for enforcing that set-like property inside a real database system.

Why Keys Are Essential for Data Organization

Keys solve three interconnected organizational problems: redundancy, retrieval speed, and cross-table relationships.

Avoiding redundancy is perhaps the most immediately visible benefit. Without keys and the referential links they enable, the only way to associate an order with a customer would be to copy the customer's name, address, and phone number into every order row. Keys allow a design where customer data lives once in a customers table, and an orders table simply stores the customer's key value — a small integer rather than a large block of repeated text. This principle underlies the process of normalization, the systematic decomposition of tables to eliminate redundant data.

Efficient retrieval is the second major benefit. Database engines almost always build an index automatically on a primary key column. An index works analogously to a book's index: instead of scanning every row from top to bottom, the engine jumps directly to the correct location. When a query filters or joins on a key column, this index makes the operation orders of magnitude faster on large tables. Even non-primary keys can be indexed explicitly to speed up frequently used lookup columns.

Meaningful cross-table relationships depend entirely on keys. Consider an e-commerce schema:

Table Key Column(s) Role
customerscustomer_idUniquely identifies each customer
ordersorder_idUniquely identifies each order
orderscustomer_idReferences the customer who placed the order
order_items(order_id, product_id)Uniquely identifies each line item in an order

Each arrow of reference between these tables is only sensible because the referenced column is a reliable, unique identifier. If customer_id in the customers table were not unique, linking an order to a customer would yield an ambiguous result — the database would not know which of several matching rows to associate with the order.

Keys and Data Integrity

Data integrity means that the values stored in a database accurately and consistently represent the real-world facts the database is meant to model. Keys enforce two distinct categories of integrity.

Entity integrity is the guarantee that every row in a table is uniquely identifiable. It is violated the moment two rows become indistinguishable — a situation that creates genuine logical problems. If two rows have identical key values, the database cannot answer the question "give me the record for customer 1001" with a single, definitive answer. SQL enforces entity integrity by rejecting any INSERT or UPDATE that would produce a duplicate key value.

Referential integrity is the guarantee that references between tables remain valid. Suppose an orders row references customer_id = 42, but no customer with that ID exists in the customers table. The order is now an orphan — it points into a void. Referential integrity constraints (implemented via foreign keys) prevent this situation both at insertion time (you cannot create an order that references a non-existent customer) and at deletion time (you cannot delete a customer who still has orders, unless the schema specifies a cascading action).

The broader consequence of missing key constraints is a class of problems known as update anomalies:

  • Insertion anomaly: You cannot record a fact without also recording an unrelated fact. For example, in an unnormalized table, you cannot add a new department unless you also have at least one employee to put in it.
  • Update anomaly: Changing a single real-world fact requires updating many rows. If a customer's address is stored in every order row, changing the address means finding and updating every one of those rows — and missing even one leaves the database in an inconsistent state.
  • Deletion anomaly: Deleting one fact inadvertently destroys another. Removing the last employee in a department might eliminate all record of that department's existence if department data is embedded in the employee rows.

Properly defined keys, combined with normalization, eliminate these anomalies by ensuring each fact is stored exactly once and referenced by key where needed elsewhere.

Overview of Key Types in SQL

SQL and the relational model recognize several distinct types of keys, each serving a particular design purpose:

  • Primary Key: The column or columns chosen as the official, authoritative identifier for rows in a table. Every table should have exactly one primary key. Primary key columns must be unique and cannot contain NULL. The database engine creates an index on the primary key automatically.
  • Foreign Key: A column or set of columns in one table whose values must match the primary key (or a unique key) of another table. Foreign keys are the mechanism for expressing relationships such as "each order belongs to a customer."
  • Candidate Key: Any column or combination of columns that could serve as a primary key — that is, it is unique and contains no nulls. A table may have several candidate keys; the designer chooses one to be the primary key, and the rest remain as unique constraints.
  • Composite Key: A key formed from two or more columns. Neither column alone is unique, but the combination is. Composite keys appear frequently in junction tables that resolve many-to-many relationships.
  • Surrogate Key: An artificial key, typically a system-generated integer or UUID, that has no business meaning. It is introduced purely for technical convenience when no natural attribute (or combination of attributes) makes a satisfactory primary key. Auto-incremented integer columns (SERIAL, AUTO_INCREMENT, IDENTITY) are the most common surrogate keys.
  • Natural Key: A key formed from attributes that have real-world meaning, such as a national identification number, an email address, or an ISBN. Natural keys avoid the need for an extra column but can become problematic if the real-world value changes (e.g., a person changes their email address).
  • Unique Key: A constraint that enforces uniqueness on a column or combination of columns without making them the primary key. Unlike primary keys, unique key columns may contain NULL (with caveats that vary by database system).

Keys as Constraints in SQL

In SQL, a key is not just a conceptual label — it is a formal constraint written into the table definition and enforced by the database engine. This is a crucial distinction: declaring a key at the database level means every application, every script, and every ad-hoc query that touches the database is subject to the same rules. It is far more robust than validating uniqueness inside application code, which can be bypassed, contain bugs, or fail to cover all paths through which data enters the database.

The principal SQL keywords used to define key constraints are:

  • PRIMARY KEY — designates the primary key of a table.
  • FOREIGN KEY ... REFERENCES — designates a foreign key and names the table and column it references.
  • UNIQUE — enforces uniqueness on a non-primary-key column or combination of columns.

These constraints can be declared either inline (as part of a column definition) or out-of-line (as a separate clause in the CREATE TABLE statement, which is required for composite keys). The following example illustrates both styles:

-- Inline primary key (single column)
CREATE TABLE customers (
    customer_id   INT          PRIMARY KEY,
    email         VARCHAR(255) UNIQUE NOT NULL,
    full_name     VARCHAR(100) NOT NULL
);

-- Out-of-line composite primary key and foreign key
CREATE TABLE order_items (
    order_id    INT  NOT NULL,
    product_id  INT  NOT NULL,
    quantity    INT  NOT NULL DEFAULT 1,
    unit_price  NUMERIC(10,2) NOT NULL,

    PRIMARY KEY (order_id, product_id),

    FOREIGN KEY (order_id)
        REFERENCES orders(order_id)
        ON DELETE CASCADE,

    FOREIGN KEY (product_id)
        REFERENCES products(product_id)
        ON DELETE RESTRICT
);

When the database engine encounters an INSERT or UPDATE that would violate a key constraint, it raises an error and rolls back the offending statement. For example, attempting to insert a second row with customer_id = 1 into the customers table above would produce an error such as "duplicate key value violates unique constraint." Similarly, trying to insert an order_items row with an order_id that does not exist in the orders table would produce a foreign key violation error.

The ON DELETE CASCADE clause in the example above instructs the database that if a parent row in orders is deleted, all matching child rows in order_items should be deleted automatically. ON DELETE RESTRICT (the default in most systems) does the opposite: it prevents the deletion of a parent row if any matching child rows exist. These options give designers fine-grained control over how referential integrity is maintained during delete (and update) operations.

Taken together, primary keys, foreign keys, and unique constraints form a network of guarantees woven directly into the database schema. Every topic that follows in this module — candidate keys, composite keys, surrogate keys, and the nuances of foreign key behavior — builds on this foundation. A solid understanding of what keys are, what problem each type solves, and how SQL expresses them as enforceable constraints is the indispensable starting point for designing databases that are correct, efficient, and maintainable.
