Database Security Fundamentals

Introduction

Database security begins long before you type a GRANT statement. It starts with a set of principles that tell you what you are protecting, from whom, and how much access any given person or program should have. In this topic you will meet those principles: the CIA Triad (confidentiality, integrity, availability), the distinction between authentication and authorization, the principle of least privilege, and the layered approach known as defense in depth.

These ideas matter in COP4708 because every practical task later in the module is an application of them. Creating users and roles is authorization in action; using parameterized queries protects integrity and confidentiality; storing credentials outside your code and encrypting connections are defense-in-depth layers; and choosing a limited service account for an application is least privilege applied to software rather than people. If the principles are clear, the SQL and configuration choices stop feeling arbitrary.

As you watch, keep a running list of two things. First, which part of the CIA Triad each control protects, since many controls protect only one or two and you need combinations to cover all three. Second, where the database sits relative to other defenses: notice that the database is rarely the first line of defense, but it is often the last, which is why access control inside the database still matters even when a network firewall and an application layer stand in front of it.

User Roles and Permissions

Introduction

Every database engine assumes that not everyone who connects should be able to do everything. User accounts identify who is connecting, privileges define what each account is allowed to do, and roles bundle privileges into reusable packages that can be granted and revoked as job responsibilities change. In this topic you will look at how accounts are created with CREATE USER, how access rights are assigned with GRANT and withdrawn with REVOKE, and how a role-based access control (RBAC) model keeps permission management manageable as the number of users grows.

Two ideas sit underneath the mechanics. The principle of least privilege says each account should hold only the rights it needs for its task and nothing more, so that a compromised or careless account causes limited damage. Separation of duties says that sensitive combinations of power — for example, the ability to both change data and erase the audit trail of that change — should not sit in a single role, and that administrative accounts should be distinct from everyday application accounts.

The videos below approach this from two directions: one conceptual video on access control models, and two hands-on walkthroughs in MySQL and Oracle. While watching the conceptual video, pay attention to how roles differ from attribute-based rules and when each approach fits. While watching the hands-on videos, note the exact syntax for creating an account, the difference between creating a user and granting that user any privileges, and how the demonstrated grants would change if you deliberately restricted them to the minimum needed.

Authentication and Authorization

Introduction

Every database interaction begins with two questions: who are you, and what are you allowed to do? Authentication answers the first by verifying identity through credentials such as passwords, keys, certificates, or tokens. Authorization answers the second by deciding which tables, views, and operations that verified identity may touch. Databases implement both as first-class features, which is why you can create users, assign roles, and issue GRANT and REVOKE statements directly in SQL rather than relying on application code to police access.

In this course the distinction matters because an application is rarely the only path to your data. If authorization rules live only in the application layer, anyone who reaches the database through another client inherits full power. Pushing rules down to the database level, and giving application service accounts only the privileges they actually need, is what makes least privilege real. Password policies and credential management round this out: stored credentials must be hashed properly, rotated sensibly, and never embedded in source code.

As you watch, keep a running list of vocabulary and map it back to SQL. When a video says "authorization," ask yourself which GRANT statement would express that. When it discusses identity providers, roles, or privilege assignment, think about how a database role groups permissions so they can be given to many users at once. For the password video, focus on why hashing and salting exist and what that implies for any credential store you design.

SQL Injection Prevention

Introduction

SQL injection is the classic example of what goes wrong when user-supplied text is treated as part of a SQL command instead of as data. An attacker types something like ' OR 1=1 -- into a login box or a URL parameter, the application pastes that string directly into a query, and the database faithfully executes whatever statement results. The consequences range from bypassing authentication to dumping entire tables, modifying records, or in some configurations running operating-system commands.

In this module, injection prevention sits alongside users, roles, and privileges because the two defenses work together. Parameterized queries and prepared statements are the primary fix: the SQL text and the parameter values travel separately, so input can never change the structure of the statement. Input validation and allowlisting narrow what is accepted in the first place, escaping and encoding handle the cases where parameters are not possible, and least privilege limits the blast radius if something does get through. Testing and code review keep the protection in place as the application changes.

As you watch, pay attention to three things: how the attacker's input changes the meaning of the query, what the fix actually does at the database driver level, and why filtering bad characters alone is a weaker strategy than parameterization. Try to connect each demonstration back to code you would write for your own application layer.

Application-to-Database Connections

Introduction

Every application that reads or writes data has to tell the database who it is, where the server lives, and how to talk to it. That information is bundled into a connection string: a host or server name, a port, a database name, a user account, credentials, and often options such as whether TLS/SSL is required. Getting the connection string right is a functional requirement; getting it stored and scoped correctly is a security requirement.

The common failure mode in real projects is hard-coding credentials directly in source files that then end up in a Git repository, a container image, or a log file. The alternative is to keep configuration outside the code: environment variables, configuration files excluded from version control, or a dedicated secrets manager or vault that issues and rotates credentials. Alongside this, the account the application uses should follow the principle of least privilege — a service account with only the SELECT, INSERT, UPDATE, or DELETE rights it actually needs, never a superuser — and the connection itself should be encrypted in transit so credentials and query results are not readable on the wire.

As you watch, keep three questions in mind. Where does the secret physically live at rest, and who or what can read it? How does the same application move between development, test, and production without editing code? And what would an attacker gain if they obtained this one set of credentials — which is really a question about how narrowly the database user was scoped.

ORM Frameworks and Database Abstraction

Introduction

An Object-Relational Mapping (ORM) framework sits between your application code and the database. Instead of writing SQL strings by hand, you define classes that map to tables and manipulate objects; the ORM translates those operations into SQL, sends them over the application's database connection, and maps the results back into objects. Popular examples include Django's built-in ORM and SQLAlchemy in Python, along with Hibernate, Entity Framework, and ActiveRecord in other ecosystems.

ORMs matter in a security module for three reasons. First, they generate parameterized SQL by default, which is the single most effective defense against SQL injection — the same protection you learn to implement manually with prepared statements. Second, they centralize data access so that every part of the application queries the database the same way, making it easier to audit and to enforce consistent behavior. Third, they do not remove your responsibility: raw-SQL escape hatches, string interpolation inside ORM calls, and overly broad service-account privileges can reintroduce exactly the vulnerabilities the ORM was supposed to prevent.

As you watch, look for how the ORM defines models and relationships, how it abstracts away vendor-specific SQL so the same code can target different database engines, and — most importantly — what the generated SQL actually looks like. Seeing the real query behind an ORM call is how you verify that values are being bound as parameters rather than concatenated into the statement, and how you connect ORM behavior back to the least-privilege and connection-strategy topics in this module.

Connection Pooling Best Practices

Introduction

Every time an application opens a database connection, work happens behind the scenes: a network socket is created, credentials are authenticated, and the database server allocates memory and a session context. That setup cost is small for one connection but crushing when an application does it for every web request. Connection pooling solves this by keeping a set of already-authenticated connections open and lending them out to application threads as needed, returning them to the pool instead of closing them.

In this course, pooling sits at the intersection of performance and security. Pool settings such as minimum and maximum pool size, connection timeout, idle timeout, and maximum connection lifetime determine whether your application scales smoothly or exhausts the database's connection limit. At the same time, a shared pool means many application users may travel over the same physical connection under one service account, which raises questions about session state leakage (temporary tables, session variables, SET ROLE changes), auditing, and applying least privilege when the database only ever sees a single login. Connection leaks — borrowed connections that are never returned because of an unhandled exception or a missing close/dispose — are a classic production failure, and ORM frameworks like Hibernate, Entity Framework, and SQLAlchemy each have their own pooling layer you need to understand rather than accept by default.

The videos below approach pooling from the systems and operations side. As you watch, look for where pooling appears in the larger list of performance techniques, how it interacts with other scaling strategies, and what connection failures actually look like from the database server's perspective. Then connect those observations back to the course material: which configuration choices would you make for a web application, and what would you still need to do in code to prevent leaks and isolate session state?
