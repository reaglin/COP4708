Introduction

Every database interaction begins with two questions: who are you, and what are you allowed to do? Authentication answers the first by verifying identity through credentials such as passwords, keys, certificates, or tokens. Authorization answers the second by deciding which tables, views, and operations that verified identity may touch. Databases implement both as first-class features, which is why you can create users, assign roles, and issue GRANT and REVOKE statements directly in SQL rather than relying on application code to police access.

In this course the distinction matters because an application is rarely the only path to your data. If authorization rules live only in the application layer, anyone who reaches the database through another client inherits full power. Pushing rules down to the database level, and giving application service accounts only the privileges they actually need, is what makes least privilege real. Password policies and credential management round this out: stored credentials must be hashed properly, rotated sensibly, and never embedded in source code.

As you watch, keep a running list of vocabulary and map it back to SQL. When a video says "authorization," ask yourself which GRANT statement would express that. When it discusses identity providers, roles, or privilege assignment, think about how a database role groups permissions so they can be given to many users at once. For the password video, focus on why hashing and salting exist and what that implies for any credential store you design.
