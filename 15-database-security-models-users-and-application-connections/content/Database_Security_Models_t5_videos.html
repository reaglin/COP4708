Introduction

Every application that reads or writes data has to tell the database who it is, where the server lives, and how to talk to it. That information is bundled into a connection string: a host or server name, a port, a database name, a user account, credentials, and often options such as whether TLS/SSL is required. Getting the connection string right is a functional requirement; getting it stored and scoped correctly is a security requirement.

The common failure mode in real projects is hard-coding credentials directly in source files that then end up in a Git repository, a container image, or a log file. The alternative is to keep configuration outside the code: environment variables, configuration files excluded from version control, or a dedicated secrets manager or vault that issues and rotates credentials. Alongside this, the account the application uses should follow the principle of least privilege — a service account with only the SELECT, INSERT, UPDATE, or DELETE rights it actually needs, never a superuser — and the connection itself should be encrypted in transit so credentials and query results are not readable on the wire.

As you watch, keep three questions in mind. Where does the secret physically live at rest, and who or what can read it? How does the same application move between development, test, and production without editing code? And what would an attacker gain if they obtained this one set of credentials — which is really a question about how narrowly the database user was scoped.
