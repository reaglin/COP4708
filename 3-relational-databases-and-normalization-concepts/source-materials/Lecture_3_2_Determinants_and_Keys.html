Lecture 3-2 Determinants and Keys

Primary Key in a Relational Database

A primary key is a unique identifier for each row (record) in a relational database table. It ensures that each row is distinct and can be easily referenced.

Properties of a Primary Key:

  1. Uniqueness: Every row in a table must have a unique primary key value. This prevents duplicate records.
  2. Non-Null: A primary key cannot be null. It must have a value for every row.
  3. Minimality: The primary key should be minimal, meaning it should contain the fewest possible columns necessary to uniquely identify each row.
  4. Immutability: While not strictly enforced in all database systems, it's generally recommended that primary keys remain unchanged once assigned. This helps maintain data integrity and relationships.

Purpose of a Primary Key:

  • Unique Identification: Ensures that each row is distinct and can be easily referenced.
  • Data Integrity: Helps maintain data consistency and prevents duplicate records.
  • Relationships: Serves as a foreign key in other tables to establish relationships between entities.
  • Indexing: Often used for indexing, which can significantly improve query performance.

Example:

In a "Customers" table, the "Customer ID" column might be the primary key. Each customer would have a unique ID, preventing duplicate records. This ID could then be used to reference customer information in other tables, such as "Orders" or "Addresses."

In summary, the primary key is a crucial component of a relational database, providing a foundation for data organization, integrity, and relationships.

Composite Key

A composite key is a primary key that consists of multiple columns (fields) within a table. When combined, these columns uniquely identify each row. This is often necessary when a single column alone cannot guarantee uniqueness.

Example:

Consider a table named "OrderItems" that stores information about items included in customer orders. In this case, a single column might not be sufficient to uniquely identify each order item. For example, if a customer orders the same item multiple times, the item's ID alone wouldn't differentiate between those instances.

A composite key could be created using the following columns:

  • OrderID: The unique identifier for the entire order.
  • ItemNumber: The unique identifier for the specific item.

By combining these two columns, each order item can be uniquely identified. For instance, "OrderID 100, ItemNumber 3" would refer to a specific item in a particular order.

When to Use a Composite Key:

  • Multiple Columns Required: When a single column cannot guarantee uniqueness.
  • Natural Relationships: When the combination of columns represents a natural relationship or identifier.
  • Performance Optimization: In some cases, using a composite key can improve query performance, especially when filtering data based on multiple columns.

In essence, a composite key is a powerful tool for ensuring data integrity and uniqueness in relational databases, especially when dealing with complex relationships and data structures.

Surrogate Key

A surrogate key is an artificially generated, unique identifier for a row in a relational database table. Unlike natural keys (columns that represent real-world attributes), surrogate keys have no intrinsic meaning within the data itself.

Characteristics of a Surrogate Key:

  • Artificially Generated: Typically created using a sequence or counter.
  • Unique: Each row in the table has a unique surrogate key value.
  • Non-Null: Cannot be null.
  • Immutable: Once assigned, it's generally recommended to remain unchanged.

Reasons for Using Surrogate Keys:

  1. Stability: Surrogate keys are more stable than natural keys, which can change over time (e.g., if a customer's name changes).
  2. Performance: Surrogate keys can often be indexed more efficiently than natural keys, especially when dealing with large datasets.
  3. Data Integrity: Using surrogate keys can help maintain data integrity by preventing accidental updates or deletions based on natural key values that might change.
  4. Simplicity: Surrogate keys are often simpler to manage and understand than natural keys, especially in complex data models.

Example:

Consider a "Customers" table. Instead of using the customer's name or email address as the primary key, a surrogate key (e.g., a numeric sequence) could be assigned to each customer. This would ensure a unique identifier for every customer, even if their name or email changes.

In summary, surrogate keys provide a reliable and efficient way to identify rows in a relational database, especially when natural keys might not be suitable or efficient.

Foreign Key: A Bridge Between Tables

A foreign key is a field in one table that references the primary key in another table. This creates a relationship between the two tables, allowing for data association.

Purpose of a Foreign Key:

  • Data Association: Establishes a connection between related entities.
  • Data Integrity: Helps maintain data consistency by ensuring that values in the foreign key column match existing values in the referenced primary key.
  • Referential Integrity: Enforces rules to prevent data inconsistencies, such as deleting a parent record that has dependent child records.

Example:

Consider two tables:

  1. Orders: Contains information about customer orders.
  2. OrderItems: Contains information about the items included in each order.

The Orders table might have a primary key column called "OrderID." In the OrderItems table, the "OrderID" column would be a foreign key, referencing the "OrderID" column in the Orders table. This indicates that each order item belongs to a specific order.

By using foreign keys, you can easily retrieve related information. For example, to find all the items included in a particular order, you can query the OrderItems table using the corresponding OrderID value.

In essence, foreign keys act as bridges between tables, allowing you to establish meaningful relationships and maintain data integrity in your relational database.
