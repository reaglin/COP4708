Introduction

An update anomaly occurs when the same fact is stored in more than one place in a table, so changing that fact correctly requires changing every copy of it. If a customer's phone number appears on fifty order rows, a single correction means fifty row updates. Miss one, and the database now contains two contradictory answers to the same question — and there is no reliable way for a query to tell which one is right.

In this module, update anomalies serve as the practical motivation for normalization. Rather than treating normal forms as abstract rules, we approach them as a response to a concrete problem: redundant storage causes partial updates, partial updates cause inconsistency, and inconsistency destroys data integrity. Recognizing the warning signs in a schema — a non-key column whose value repeats across many rows because it really describes a different entity — is the diagnostic skill that makes the rest of normalization make sense.

As you watch the videos below, pay attention to three things. First, how each example identifies which column is being duplicated and why. Second, how the update anomaly differs from insertion and deletion anomalies, since all three come from the same root cause but show up differently. Third, how splitting a table into separate tables linked by keys reduces each fact to a single stored copy, so that one update is genuinely enough.

How These Videos Support the Learning Outcomes

Together these videos move from symptom to cure. The Boekhoven video directly serves MO2 by separating insertion, update, and deletion anomalies and showing each in a poorly structured schema, while its examples of duplicated values help you recognize the warning signs described in MO3. The Gate Smashers and Lowgren videos address MO4 and MO5 by explaining how each normal form removes a specific class of redundancy and by demonstrating the decomposition of a badly designed table into tables that each describe one entity. Both normalization videos also reinforce MO1, since every decomposition depends on correctly identifying rows, columns, and the primary and foreign keys that reconnect the resulting tables.
