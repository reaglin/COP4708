Introduction to Relational Databases

Introduction

A relational database organizes information into tables, where each row represents one instance of something (a customer, an order, a course section) and each column represents one attribute of that thing. What makes the model "relational" is that tables are not isolated: a primary key uniquely identifies each row in a table, and a foreign key stored in another table points back to that key, letting you connect related facts without copying them everywhere.

This topic matters because every later idea in this module depends on it. Normalization, anomalies, and the warning signs of bad table design only make sense once you can look at a schema and say what entity each table describes, what identifies a row, and how the tables link together. Poorly structured data, where one table tries to hold several unrelated entities or repeats the same fact in many rows, is what creates the update and deletion problems you will study next.

As you watch, keep three questions in mind for every example shown: What single thing does this table describe? What column or combination of columns uniquely identifies a row? And where does one table reference another? Sketch the tables and draw the links yourself rather than only watching; the habit of diagramming structure is what you will be graded on later in the module.

Problems with Poorly Structured Tables

Introduction

When a single table is asked to store too much at once — customers, orders, products, and salespeople all jammed together — the same facts end up repeated in row after row. That repetition is called data redundancy, and it is the root cause of the three classic problems you will study here: insertion anomalies (you cannot record one fact without inventing another), update anomalies (changing one fact requires finding and editing many rows, and missing one leaves the data contradictory), and deletion anomalies (removing one row accidentally destroys unrelated information).

This topic matters because it supplies the motivation for everything that follows in the module. Normalization can feel like an abstract set of rules until you have seen a concrete badly designed table and felt why it hurts. Once you can point at a schema and say "this column repeats, this table mixes two entity types, this fact depends on only part of the key," the normal forms stop being memorization and become a repair procedure.

As you watch, keep a simple checklist in mind: Which values repeat unnecessarily? If I changed one of those values, how many rows would I have to touch? What happens if I delete this row — do I lose something I still need? And what single real-world thing is this table actually about? Try pausing each video when a sample table appears and diagnosing it yourself before the narrator does.

Insertion Anomalies

Introduction

An insertion anomaly happens when the design of a table prevents you from recording a fact you legitimately want to store, because the table also demands unrelated information that does not yet exist. A classic example is a table that mixes two different kinds of entities — say, courses and the instructors assigned to them. If the table's primary key requires an instructor, you cannot record a newly approved course until someone is hired to teach it. The problem is not the data; it is the structure.

In this module, insertion anomalies are one of three related symptoms (alongside update and deletion anomalies) that signal unwanted dependencies in a schema. Watch for the ways designers try to work around the problem rather than fix it: leaving columns NULL, or inventing placeholder rows such as "TBD" or instructor ID 0000. These workarounds look harmless but corrode data integrity, since NULLs and dummy values propagate into queries, joins, constraints, and reports. The real fix is decomposition — splitting the table so each table describes one logical entity, with dependencies pointing only at the whole key.

As you watch the videos below, keep two questions in mind. First, which functional dependency in the example table is the culprit — what determines what, and is that determinant actually a key? Second, after the table is decomposed, which rows could now be inserted independently that could not be inserted before? Being able to narrate that before-and-after story is exactly what the module outcomes ask of you.

Update Anomalies

Introduction

An update anomaly occurs when the same fact is stored in more than one place in a table, so changing that fact correctly requires changing every copy of it. If a customer's phone number appears on fifty order rows, a single correction means fifty row updates. Miss one, and the database now contains two contradictory answers to the same question — and there is no reliable way for a query to tell which one is right.

In this module, update anomalies serve as the practical motivation for normalization. Rather than treating normal forms as abstract rules, we approach them as a response to a concrete problem: redundant storage causes partial updates, partial updates cause inconsistency, and inconsistency destroys data integrity. Recognizing the warning signs in a schema — a non-key column whose value repeats across many rows because it really describes a different entity — is the diagnostic skill that makes the rest of normalization make sense.

As you watch the videos below, pay attention to three things. First, how each example identifies which column is being duplicated and why. Second, how the update anomaly differs from insertion and deletion anomalies, since all three come from the same root cause but show up differently. Third, how splitting a table into separate tables linked by keys reduces each fact to a single stored copy, so that one update is genuinely enough.

Deletion Anomalies

Introduction

A deletion anomaly happens when removing one piece of information from a table accidentally destroys other, unrelated information that happened to be stored in the same row. If a single table mixes facts about two different things — say, a course and the instructor who teaches it — then deleting the last row about a course can also erase the only record of that instructor. The data was never intentionally discarded; it simply had nowhere else to live.

This matters in COP4708 because deletion anomalies are one of the three classic symptoms (along with insertion and update anomalies) that signal a table is doing too many jobs at once. Recognizing the symptom is the first step; the cure is normalization, which separates tightly coupled data into tables that each describe a single logical entity, linked by keys. Once the instructor lives in her own table, deleting a course row cannot take her with it.

As you watch the videos below, look for three things: (1) examples where one row holds facts about more than one entity, (2) the moment a presenter shows what is lost when a row is deleted, and (3) how splitting a table and introducing keys and foreign keys makes the loss impossible. Also pay attention to the denormalization video's discussion of trade-offs — it will help you see why anomalies are the price paid when tables are deliberately merged.

Introduction to Normalization

Introduction

Normalization is a systematic method for organizing the tables of a relational database so that each table stores facts about one thing, and each fact is stored in exactly one place. Rather than being an arbitrary set of rules, normalization is a response to concrete problems: when the same data is repeated across many rows, the database becomes vulnerable to inconsistency, and ordinary operations like adding, changing, or removing a row can produce unintended side effects. These side effects are called insertion, update, and deletion anomalies, and they are the core motivation for everything that follows in this module.

In this course, normalization connects the structural vocabulary you already have (tables, rows, columns, keys) to the practical work of schema design. You will see that normal forms are a progressive framework: each form assumes the previous one and removes a specific category of problematic dependency. Understanding this progression lets you look at an existing table, name what is wrong with it, and justify the decomposition you propose instead of guessing.

As you watch the videos below, keep three questions in mind. First, what specific anomaly or redundancy is each rule designed to prevent? Second, what does the "before" table look like versus the "after" tables, and how are they reconnected through keys? Third, where do the presenters acknowledge trade-offs, such as the extra joins that a highly normalized design can require? Take notes on the example tables used, since you will be asked to perform similar decompositions yourself.
