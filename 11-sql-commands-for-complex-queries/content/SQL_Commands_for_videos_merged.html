Introduction to Complex SQL Queries

Introduction

A complex SQL query is one that pulls data from more than one table, filters it in several ways, groups it, or nests one query inside another. Instead of asking a single simple question like "list all customers," complex queries answer layered business questions such as "which product categories had average order values above a certain amount last quarter, and which sales representatives handled them?" The answer lives across multiple related tables, so you need JOINs, WHERE and HAVING conditions, GROUP BY with aggregate functions, and sometimes subqueries, all working together in one statement.

This topic sets the foundation for the rest of the module. Before you can write a complex query confidently, you need a clear mental model of how relational tables connect through primary and foreign keys, and you need to understand the order in which SQL clauses are evaluated. That execution order explains, for example, why WHERE filters individual rows before grouping while HAVING filters groups after aggregation. Recognizing the core building blocks also makes long queries far less intimidating: almost every large query is a collection of familiar small pieces.

As you watch the videos below, look for the progression from a simple SELECT to a multi-table, multi-clause statement. Pay attention to how experienced developers break a query apart, test one piece at a time, and build upward rather than typing the whole thing at once. Try to identify each clause by name and ask yourself what it contributes to the final result set.

JOIN Types and Multi-Table Queries

Introduction

Relational databases deliberately split information across multiple tables to avoid duplication: customers live in one table, orders in another, products in a third. That design keeps data clean, but it means almost every useful question you ask will require pulling columns from more than one table at a time. JOINs are the SQL mechanism that makes this possible, matching rows from one table to rows in another based on a shared key.

In this topic you will work through the four primary JOIN types. An INNER JOIN returns only rows that have a match on both sides. A LEFT JOIN keeps every row from the left table and fills in NULLs where no match exists on the right; a RIGHT JOIN does the mirror image; and a FULL JOIN preserves unmatched rows from both tables. The differences matter enormously in practice — the same query written with INNER instead of LEFT can silently drop the customers who have not yet placed an order, which is often exactly the group you were trying to count.

As you watch the videos below, pay close attention to three things: the join condition (the ON clause and which columns it compares), where NULLs appear in the result set and why, and how table aliases keep multi-table queries readable. When a video shows a diagram or animation, try to connect the picture back to the actual rows in the result table rather than memorizing the shape alone. Then practice writing the queries yourself — JOIN syntax becomes intuitive quickly once you have typed a dozen of them.

Filtering Data with WHERE Clauses

Introduction

Every SQL query you write returns rows, but rarely do you want all of them. The WHERE clause is the mechanism that lets you state, precisely and declaratively, which rows qualify: customers in a particular region, orders above a dollar threshold, product names that begin with a certain prefix, or records where a value was never recorded at all. Understanding WHERE is the foundation for nearly everything else in this module, because joins, grouped summaries, and subqueries all depend on your ability to express conditions accurately.

In this topic you will work through the building blocks one at a time: the basic structure of a WHERE clause, the comparison operators (=, <>, <, >, <=, >=, BETWEEN), the logical operators AND, OR, and NOT, pattern matching with LIKE and its wildcards, set membership with IN and NOT IN, and the special handling that NULL requires through IS NULL and IS NOT NULL. The last subtopic ties these together: combining several conditions in one predicate, where operator precedence and parentheses determine whether your query means what you think it means.

As you watch the videos below, pay attention to the exact syntax used, especially how string literals are quoted, how wildcards (% and _) behave, and why NULL cannot be tested with the equals sign. Try pausing and predicting which rows a given condition will return before the presenter runs the query — that habit is what turns syntax recognition into real query-writing skill.

Sorting Results with ORDER BY

Introduction

A SELECT statement returns a set of rows, and unless you say otherwise, the database makes no promise about the order in which those rows come back. The ORDER BY clause is how you take control of that sequence, telling the database to present results sorted by one or more columns, ascending or descending. It is the last major clause evaluated in a query, which is why it can reference column aliases and even column positions that earlier clauses cannot.

In this module you are building complex queries with joins, grouping, and subqueries. Sorting is what makes those results readable and usable: a grouped sales summary is far more informative when ordered from highest total to lowest, and a filtered customer list is easier to scan when ordered by last name then first name. You will also see that sorting behaves differently depending on data type — numbers sort numerically, text sorts by collation rules, and dates sort chronologically — and that NULL values need special attention.

As you watch, pay attention to the exact syntax (ASC is the default and can be omitted, DESC must be stated explicitly), to how a second or third sort column acts as a tiebreaker, and to how sorting interacts with row limits such as LIMIT or TOP. Also note where sorting by column position is convenient and where it becomes fragile if the SELECT list changes.

Aggregating Data with GROUP BY and HAVING

Introduction

Up to this point, most of your queries have returned individual rows. GROUP BY changes that perspective: instead of looking at each row on its own, you collapse rows that share a common value into a single summary row. Combined with aggregate functions such as COUNT, SUM, AVG, MIN, and MAX, GROUP BY lets you answer questions like "how many orders did each customer place?" or "what is the average salary in each department?" — the kind of statistical summaries that turn raw stored data into useful information.

HAVING is the companion clause that filters those summary groups. A common source of confusion is why you cannot simply put an aggregate condition in WHERE, and the answer lies in query execution order: WHERE filters individual rows before grouping happens, while HAVING filters the groups after the aggregates have been calculated. Keeping that sequence straight (FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY) is the single most helpful mental model for this topic, and it is also exactly what the module outcomes ask you to be able to explain.

As you watch the videos below, pay attention to three things: which columns appear in the SELECT list versus the GROUP BY list, where each example places a filtering condition and why, and how the final query reads from top to bottom once GROUP BY and HAVING are combined. Try pausing and predicting the result set before the presenter runs the query — that habit will prepare you well for the module assignments.

Writing and Using Subqueries

Introduction

A subquery is simply a SELECT statement nested inside another SQL statement. Instead of running one query, writing down the result, and then typing a second query that uses that result, you let the database do both steps at once. The inner query runs and hands its result to the outer query, which uses it as a value, a list of values, or even a temporary table.

Where you place the subquery determines what it does. In the WHERE clause, a subquery supplies values to filter on, often with operators such as =, IN, >, or ALL/ANY. In the FROM clause, it acts as a derived table — a result set you can join to or filter like any other table. In the SELECT clause, a scalar subquery returns exactly one value per row, useful for adding a computed column such as a count or an average. You will also meet correlated subqueries, which reference a column from the outer query and therefore re-evaluate for each outer row, and the EXISTS / NOT EXISTS operators, which test whether a subquery returns any rows at all.

As you watch the videos below, pay attention to three things: where the subquery sits in the statement, how many rows and columns it is allowed to return in that position, and whether it depends on the outer query (correlated) or can run on its own (non-correlated). Try pausing and predicting the result before the presenter reveals it, and notice when a subquery could have been written more simply as a JOIN — that judgment is part of good practice.
