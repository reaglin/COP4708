Introduction

Most people meet SQL as a query language — a way to ask questions of data that already exists. In this module we shift the emphasis: before anything can be queried, something has to define what tables exist, what columns they hold, what data types those columns accept, and what rules keep the data consistent. That defining work is done in SQL too, through its Data Definition Language (DDL) commands such as CREATE DATABASE, CREATE TABLE, ALTER, and DROP. In this sense SQL is not only a retrieval tool but a data modeling language — a notation for writing down a model of a problem domain in a form a relational database management system can actually execute.

This matters because it is the point where design becomes reality. A conceptual model (entities and relationships) is refined into a logical model (relations, attributes, keys, normalization), and SQL DDL is what turns that logical model into a physical structure inside a specific RDBMS such as MySQL, PostgreSQL, Oracle, or SQL Server. Every choice you made during design — identifiers, relationships, optionality, business rules — must reappear as a primary key, a foreign key, a NOT NULL, a UNIQUE, or a CHECK constraint. If it does not appear in the DDL, the database does not enforce it.

As you watch the videos below, keep three questions in mind. First, which parts of a design diagram translate directly into SQL statements, and which require judgment calls? Second, how are relationships between entities actually represented in physical SQL, given that tables cannot literally "connect" except through key columns? Third, where does each DDL command fit in the overall design workflow — what has to be decided before you are ready to type CREATE TABLE at all?
