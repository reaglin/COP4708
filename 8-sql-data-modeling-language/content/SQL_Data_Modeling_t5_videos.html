Introduction

Before you write a single CREATE TABLE statement, a database normally passes through three design phases: conceptual design (what things the business cares about and how they relate), logical design (entities, attributes, keys, and relationships expressed in the relational model), and physical design (how that model is actually built in a particular DBMS). SQL lives mostly in that third phase. It is the implementation layer — the language in which the decisions you already made on paper or in a diagram become real tables, columns, data types, and constraints.

This matters in COP4708 because the quality of your SQL schema is largely decided before you start typing. A clean logical model maps almost mechanically to SQL: each entity becomes a table, each attribute becomes a column with a data type, each identifier becomes a primary key, and each relationship becomes a foreign key. A muddled model produces a schema that fights you later. Design is also iterative — writing the SQL often exposes an ambiguity or a missing rule, sending you back to revise the model before moving forward again.

The three videos below come from Database Star, a channel focused on practical database design and SQL. As you watch, try to separate the design reasoning from the SQL syntax: notice where the presenter is making a modeling decision (what is an entity? what is the key? is this one-to-many or many-to-many?) and ask yourself what SQL statement or constraint would express that decision. Also pay attention to the moments where a design is revised mid-process — that is the iterative refinement loop in action.

How These Videos Support the Learning Outcomes

Together these videos support the module outcomes by supplying the design context that SQL implements.
