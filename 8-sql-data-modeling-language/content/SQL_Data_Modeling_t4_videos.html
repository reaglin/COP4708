Introduction

A database schema is the formal blueprint of a database: it names the tables, the columns in each table, the data type each column holds, and the rules that govern what values are allowed and how tables relate to one another. In this topic you move from the logical data model you produced earlier in the course to actual SQL statements — CREATE DATABASE to establish the container, and CREATE TABLE to define each entity as a physical table. This is SQL's Data Definition Language (DDL) side, distinct from the SELECT-oriented querying work you have done before.

Much of the care in schema creation goes into the details: choosing a data type that matches the real nature of the data (integers, decimals, fixed- and variable-length text, dates), declaring a PRIMARY KEY so every row is uniquely identifiable, declaring FOREIGN KEY references so related tables stay consistent, and adding column-level constraints such as NOT NULL, UNIQUE, DEFAULT, and CHECK to encode business rules directly in the schema. Constraints matter because they push rule enforcement into the database itself rather than relying on every application that touches the data.

As you watch the videos below, keep a few questions in mind. Which clause establishes identity (primary key) versus which clause establishes a relationship (foreign key)? What happens when you try to insert or delete a row that would break a reference? And how does the order in which you create tables matter when one table refers to another? Note that SQL syntax varies slightly across database products, so compare what you see on screen with the syntax used in your course environment.
