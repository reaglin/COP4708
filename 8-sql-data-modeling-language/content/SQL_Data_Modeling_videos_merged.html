Introduction to SQL as a Data Modeling Language

Introduction

Most people meet SQL as a query language — a way to ask questions of data that already exists. In this module we shift the emphasis: before anything can be queried, something has to define what tables exist, what columns they hold, what data types those columns accept, and what rules keep the data consistent. That defining work is done in SQL too, through its Data Definition Language (DDL) commands such as CREATE DATABASE, CREATE TABLE, ALTER, and DROP. In this sense SQL is not only a retrieval tool but a data modeling language — a notation for writing down a model of a problem domain in a form a relational database management system can actually execute.

This matters because it is the point where design becomes reality. A conceptual model (entities and relationships) is refined into a logical model (relations, attributes, keys, normalization), and SQL DDL is what turns that logical model into a physical structure inside a specific RDBMS such as MySQL, PostgreSQL, Oracle, or SQL Server. Every choice you made during design — identifiers, relationships, optionality, business rules — must reappear as a primary key, a foreign key, a NOT NULL, a UNIQUE, or a CHECK constraint. If it does not appear in the DDL, the database does not enforce it.

As you watch the videos below, keep three questions in mind. First, which parts of a design diagram translate directly into SQL statements, and which require judgment calls? Second, how are relationships between entities actually represented in physical SQL, given that tables cannot literally "connect" except through key columns? Third, where does each DDL command fit in the overall design workflow — what has to be decided before you are ready to type CREATE TABLE at all?

Relational Database Fundamentals

Introduction

Before you can write SQL that defines a database, you need a clear mental picture of what a relational database actually is. In the relational model, data is stored in tables (also called relations), each table holds rows (records) that represent individual things or events, and each row is made up of columns (attributes) that hold a single piece of typed data. Tables are not isolated: they are connected to one another through shared key values, which is what lets you store a customer once and reference that customer from thousands of orders without repeating the data.

This matters in COP4708 because every CREATE TABLE statement you write in this module is a direct translation of these ideas. A table definition names the relation, the column list fixes the attributes and their data types, and primary and foreign key constraints encode the relationships. Schemas sit above all of this as the organizing container that groups related tables inside a database.

As you watch the videos below, pay attention to three things: the vocabulary (table, row, column, key, schema) and how consistently it is used; how the speakers describe the connection between two tables and the role keys play in that connection; and the trade-offs that make the relational model a good fit for structured, rule-governed data. Those trade-offs will help you understand why SQL's data definition features look the way they do.

Logical Data Modeling Concepts

Introduction

Before you write a single CREATE TABLE statement, someone has to decide what things the database must keep track of, what facts describe each of those things, and how those things relate to one another. That work is logical data modeling. A logical model names the entities in a business domain, lists their attributes, identifies which attribute (or combination) uniquely identifies each instance, and records the relationships and rules that connect entities — all without committing to a particular database product or SQL dialect.

In this module, the logical model is the bridge between understanding a business problem and expressing it in SQL. Entities become tables, attributes become columns, unique identifiers become primary keys, relationships become foreign keys, and business rules become constraints. Normalization — organizing attributes so each fact is stored once, in the place it belongs — is done at the logical level so that the schema you later define is free of avoidable redundancy and update problems.

As you watch the videos below, keep a translation column in your notes. For every modeling term you hear (entity, attribute, cardinality, identifier, many-to-many relationship, bridge table), write the SQL element it will become. Pay particular attention to how one-to-many and many-to-many relationships are represented, since those decisions drive the foreign key and junction-table work you will do in the hands-on portion of this module.

Schema Creation and Definition

Introduction

A database schema is the formal blueprint of a database: it names the tables, the columns in each table, the data type each column holds, and the rules that govern what values are allowed and how tables relate to one another. In this topic you move from the logical data model you produced earlier in the course to actual SQL statements — CREATE DATABASE to establish the container, and CREATE TABLE to define each entity as a physical table. This is SQL's Data Definition Language (DDL) side, distinct from the SELECT-oriented querying work you have done before.

Much of the care in schema creation goes into the details: choosing a data type that matches the real nature of the data (integers, decimals, fixed- and variable-length text, dates), declaring a PRIMARY KEY so every row is uniquely identifiable, declaring FOREIGN KEY references so related tables stay consistent, and adding column-level constraints such as NOT NULL, UNIQUE, DEFAULT, and CHECK to encode business rules directly in the schema. Constraints matter because they push rule enforcement into the database itself rather than relying on every application that touches the data.

As you watch the videos below, keep a few questions in mind. Which clause establishes identity (primary key) versus which clause establishes a relationship (foreign key)? What happens when you try to insert or delete a row that would break a reference? And how does the order in which you create tables matter when one table refers to another? Note that SQL syntax varies slightly across database products, so compare what you see on screen with the syntax used in your course environment.

SQL in the Database Design Workflow

Introduction

Before you write a single CREATE TABLE statement, a database normally passes through three design phases: conceptual design (what things the business cares about and how they relate), logical design (entities, attributes, keys, and relationships expressed in the relational model), and physical design (how that model is actually built in a particular DBMS). SQL lives mostly in that third phase. It is the implementation layer — the language in which the decisions you already made on paper or in a diagram become real tables, columns, data types, and constraints.

This matters in COP4708 because the quality of your SQL schema is largely decided before you start typing. A clean logical model maps almost mechanically to SQL: each entity becomes a table, each attribute becomes a column with a data type, each identifier becomes a primary key, and each relationship becomes a foreign key. A muddled model produces a schema that fights you later. Design is also iterative — writing the SQL often exposes an ambiguity or a missing rule, sending you back to revise the model before moving forward again.

The three videos below come from Database Star, a channel focused on practical database design and SQL. As you watch, try to separate the design reasoning from the SQL syntax: notice where the presenter is making a modeling decision (what is an entity? what is the key? is this one-to-many or many-to-many?) and ask yourself what SQL statement or constraint would express that decision. Also pay attention to the moments where a design is revised mid-process — that is the iterative refinement loop in action.
