Introduction

Almost every database you will build in practice is used by more than one person at a time. A web storefront may have hundreds of shoppers reading inventory and placing orders in the same second; a campus registration system may have thousands of students competing for the same seats. A multi-user database environment is simply one in which many transactions are in flight concurrently, and that simple fact changes nearly everything about how you design, reason about, and test your schema and application logic.

The core challenge is simultaneous data modification. When two transactions read and write the same rows in an interleaved order, the database can end up in a state that neither transaction intended. The classic symptoms have names you will use for the rest of this module and the rest of your career: dirty reads, lost updates, non-repeatable reads, phantom reads, and incorrect (inconsistent) summaries. These problems are not bugs in the DBMS; they are the natural consequence of interleaving, and they are why single-user design assumptions break down. Logic that is obviously correct when you are the only user can silently corrupt data once a second user arrives.

The videos below set up that foundation. As you watch, focus on three things: the step-by-step interleaving that produces each anomaly (write the timelines out yourself), the vocabulary used to name each problem, and the idea that transactions must satisfy certain guarantees — the ACID properties — for concurrent access to be safe. You are not yet expected to choose isolation levels or locking strategies; you are building the mental model that makes those later choices meaningful.
