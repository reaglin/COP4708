Introduction

A deadlock happens when two or more transactions each hold a lock the other needs, so none of them can move forward. Transaction A holds a lock on row 1 and asks for row 2; transaction B holds row 2 and asks for row 1. Neither will release what it holds until it gets what it wants, so the wait is circular and permanent unless the database steps in. This is different from ordinary blocking, where one transaction simply waits for another that will eventually finish and commit.

Because a deadlock cannot resolve itself, database engines must detect the cycle and break it by choosing a victim transaction to roll back, or avoid the cycle entirely through prevention strategies such as consistent lock ordering, shorter transactions, lower lock footprints, and timeout policies that abandon a wait after a set interval. Victim selection is usually based on which transaction is cheapest to undo, though the rolled-back transaction's work is lost and must be retried by the application. This topic matters in this course because the locking and isolation choices you studied earlier directly determine how often deadlocks occur in a real multi-user system.

As you watch, look for three things: the exact interleaving of lock requests that forms the cycle, how the engine reports and diagnoses the deadlock (error messages, deadlock graphs, trace or Extended Events output), and what the presenter recommends to reduce recurrence. Keep in mind that the videos use SQL Server and Azure SQL as their demonstration platform; the specific tools differ across engines, but the underlying cycle, detection, and victim-selection logic are general.
