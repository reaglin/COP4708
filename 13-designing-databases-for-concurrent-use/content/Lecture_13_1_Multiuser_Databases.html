Lecture 13-1 Multiuser Databases

Databases employ several key mechanisms to ensure data integrity in multi-user environments, preventing inconsistencies and maintaining data accuracy even with concurrent access. Here's a breakdown of the core methods:

1. Transactions:

  • ACID Properties: Transactions are the foundation of data integrity. They guarantee Atomicity, Consistency, Isolation, and Durability (ACID):
    • Atomicity: A transaction is treated as a single, indivisible unit of work. Either all changes within the transaction are made, or none are. Partial updates are prevented.
    • Consistency: A transaction maintains the database's integrity constraints. It moves the database from one valid state to another.
    • Isolation: Transactions are isolated from each other. Concurrent transactions appear to execute as if they were serial (one after the other), preventing interference.
    • Durability: Once a transaction is committed, the changes are permanent, even in the event of system failures.
  • How They Work: Transactions group multiple database operations (inserts, updates, deletes) into a logical unit. If any part of the transaction fails, the entire transaction can be rolled back, restoring the database to its previous consistent state.

2. Concurrency Control:

  • Purpose: Manages simultaneous access to the database by multiple users, preventing conflicts and ensuring data consistency.
  • Locking: One of the most common concurrency control mechanisms. Locks prevent other transactions from accessing data that is currently being modified. Different types of locks exist (shared locks for reading, exclusive locks for writing).
  • Optimistic Concurrency Control: Assumes that conflicts are rare. Transactions proceed without acquiring locks, but before committing, they check for conflicts. If a conflict is detected, the transaction is rolled back.
  • Multi-Version Concurrency Control (MVCC): Maintains multiple versions of data. Each transaction sees a snapshot of the data, preventing read operations from blocking write operations and vice-versa. This improves concurrency and performance.

3. Constraints:

  • Data Validation: Constraints are rules that define what data is allowed in a table. They are enforced by the database to prevent invalid data from being entered.
  • Types of Constraints:
    • Primary Key: Uniquely identifies each row in a table. Ensures uniqueness and non-nullability.
    • Foreign Key: Establishes a link between two tables. Ensures referential integrity (that related data exists in the linked table).
    • Unique Constraint: Ensures that a column or set of columns has unique values (other than the primary key).
    • Check Constraint: Defines a condition that must be true for data in a column.
    • Not Null Constraint: Ensures that a column cannot have null values.

4. Triggers:

  • Automated Actions: Triggers are stored procedures that are automatically executed in response to certain events on a table (e.g., insert, update, delete).
  • Enforcing Business Rules: Triggers can be used to enforce complex business rules that cannot be easily expressed with constraints.
  • Auditing: Triggers can be used to track changes to data, creating an audit trail.

5. Data Validation at the Application Level:

  • Complementary to Database Constraints: While database constraints are essential, data validation should also be performed at the application level.
  • User-Friendly Feedback: Application-level validation can provide more specific and user-friendly error messages.
  • Pre-emptive Checks: Can catch errors before they are sent to the database, reducing the load on the database server.

6. Backup and Recovery:

  • Protecting Against Data Loss: Regular backups are crucial for protecting against data loss due to hardware failures, software errors, or human mistakes.
  • Recovery Procedures: Databases provide recovery mechanisms to restore the database to a consistent state after a failure.

7. Access Control:

  • Restricting Access: Databases provide mechanisms to control who can access and modify data.
  • Permissions and Roles: Users are granted specific permissions on database objects (tables, views, etc.). Roles can be used to group permissions together for easier management.

Example: A scenario illustrating several of these concepts:

Imagine two users, Alice and Bob, are simultaneously trying to update the quantity of a product in an inventory database.

  1. Transaction: Both Alice's and Bob's updates are treated as separate transactions.
  2. Locking (or MVCC): The database uses locking (or MVCC) to ensure that Alice's update doesn't interfere with Bob's update, and vice-versa. One user might acquire a lock on the product row while updating it.
  3. Constraint: A check constraint might ensure that the quantity of a product cannot be negative. If either Alice or Bob tries to update the quantity to a negative value, the transaction will be rolled back due to the constraint violation.
  4. Trigger: A trigger might be fired after a successful update to the product quantity, updating a related table that tracks inventory changes.

By combining these mechanisms, databases ensure that data remains consistent and reliable even in complex multi-user environments, preventing data corruption and maintaining the integrity of the information.
