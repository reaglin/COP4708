Introduction to Multi-User Database Environments

Introduction

Almost every database you will build in practice is used by more than one person at a time. A web storefront may have hundreds of shoppers reading inventory and placing orders in the same second; a campus registration system may have thousands of students competing for the same seats. A multi-user database environment is simply one in which many transactions are in flight concurrently, and that simple fact changes nearly everything about how you design, reason about, and test your schema and application logic.

The core challenge is simultaneous data modification. When two transactions read and write the same rows in an interleaved order, the database can end up in a state that neither transaction intended. The classic symptoms have names you will use for the rest of this module and the rest of your career: dirty reads, lost updates, non-repeatable reads, phantom reads, and incorrect (inconsistent) summaries. These problems are not bugs in the DBMS; they are the natural consequence of interleaving, and they are why single-user design assumptions break down. Logic that is obviously correct when you are the only user can silently corrupt data once a second user arrives.

The videos below set up that foundation. As you watch, focus on three things: the step-by-step interleaving that produces each anomaly (write the timelines out yourself), the vocabulary used to name each problem, and the idea that transactions must satisfy certain guarantees — the ACID properties — for concurrent access to be safe. You are not yet expected to choose isolation levels or locking strategies; you are building the mental model that makes those later choices meaningful.

Transactions and ACID Properties

Introduction

A database transaction is a unit of work made up of one or more operations that the database system treats as a single, indivisible action. The classic example is a funds transfer: subtracting money from one account and adding it to another must either both happen or neither happen. When many users hit the same database at the same time, this grouping is what keeps the data from drifting into states that make no sense.

The four ACID properties — Atomicity, Consistency, Isolation, and Durability — describe the guarantees a transactional database makes. Atomicity means all-or-nothing execution; Consistency means a transaction moves the database from one valid state to another without violating constraints; Isolation means concurrent transactions do not expose each other's partial work; Durability means once a transaction commits, its effects survive crashes and restarts. These four ideas are the foundation for everything else in this module, including isolation levels, concurrency anomalies, locking, and deadlock handling.

As you watch the videos below, keep three questions in mind. First, what does each property protect against — what specific bad outcome would occur without it? Second, how is each property actually implemented (logs, locks, versioning, commit protocols)? Third, where do the properties trade off against each other, especially Isolation versus performance, since that trade-off is exactly what isolation levels let you tune later in this module.

Concurrency Problems and Data Conflicts

Introduction

When only one person uses a database at a time, correctness is easy. Real systems, though, run many transactions at once, and the database interleaves their reads and writes to keep throughput high. That interleaving is where trouble starts: if two transactions touch the same rows at the wrong moments, one of them can read data that was never committed, see different values on repeated reads, or silently overwrite another user's work.

This topic gives names to those failures so you can recognize them precisely. A dirty read happens when a transaction reads uncommitted data that is later rolled back. A non-repeatable read occurs when a transaction re-reads a row and finds it changed. A phantom read occurs when a repeated query returns a different set of rows because another transaction inserted or deleted data matching the search condition. A lost update occurs when two transactions read the same value, each computes a new value, and the second write erases the first. Each of these is a specific pattern of interleaved operations, not a vague "bug" — and each one chips away at data integrity in ways that are hard to detect after the fact.

As you watch, focus on the timelines. Try to redraw each scenario as two columns, Transaction A and Transaction B, with the read, write, commit, and rollback steps in order, and mark the exact moment the anomaly becomes possible. Being able to produce that diagram from memory is the skill you will need later in the module when you choose isolation levels and concurrency control strategies.

Locking Mechanisms

Introduction

When many users read and write the same data at the same time, a database needs a way to decide who may touch what, and when. Locking is the most common mechanism for making that decision. A shared (read) lock lets several transactions read the same item concurrently, while an exclusive (write) lock gives one transaction sole access so that no one else reads or modifies the item mid-change. Intent locks sit above these at coarser levels of the data hierarchy, signaling that a transaction holds or plans to hold locks further down so the engine can detect conflicts without inspecting every row.

Lock granularity is the second half of the picture: a lock can cover a single row, a page, a partition, or an entire table. Fine granularity allows more concurrency but costs memory and bookkeeping, so engines perform lock escalation, converting many fine-grained locks into one coarse lock once a threshold is crossed. That conversion protects the lock manager but can suddenly block other users. This is the central trade-off of the topic and of this course module: more locking means stronger data protection and fewer anomalies, while less locking means better throughput and more risk.

As you watch the videos below, keep three questions in mind. First, which lock modes are compatible with which others, and why does that compatibility matrix matter? Second, at what level of the data hierarchy is each lock being taken? Third, what happens when locks collide — blocking, waiting, or deadlock — and what does the database do about it? Connect what you see to the isolation levels and concurrency anomalies covered elsewhere in this module, since isolation levels are largely implemented through locking behavior.

Deadlocks and Conflict Resolution

Introduction

A deadlock happens when two or more transactions each hold a lock the other needs, so none of them can move forward. Transaction A holds a lock on row 1 and asks for row 2; transaction B holds row 2 and asks for row 1. Neither will release what it holds until it gets what it wants, so the wait is circular and permanent unless the database steps in. This is different from ordinary blocking, where one transaction simply waits for another that will eventually finish and commit.

Because a deadlock cannot resolve itself, database engines must detect the cycle and break it by choosing a victim transaction to roll back, or avoid the cycle entirely through prevention strategies such as consistent lock ordering, shorter transactions, lower lock footprints, and timeout policies that abandon a wait after a set interval. Victim selection is usually based on which transaction is cheapest to undo, though the rolled-back transaction's work is lost and must be retried by the application. This topic matters in this course because the locking and isolation choices you studied earlier directly determine how often deadlocks occur in a real multi-user system.

As you watch, look for three things: the exact interleaving of lock requests that forms the cycle, how the engine reports and diagnoses the deadlock (error messages, deadlock graphs, trace or Extended Events output), and what the presenter recommends to reduce recurrence. Keep in mind that the videos use SQL Server and Azure SQL as their demonstration platform; the specific tools differ across engines, but the underlying cycle, detection, and victim-selection logic are general.

Transaction Isolation Levels

Introduction

When many users read and write the same data at the same time, a database must decide how much one transaction is allowed to see of another transaction's in-progress work. Transaction isolation levels are the standard knobs for that decision. The SQL standard defines four of them — Read Uncommitted, Read Committed, Repeatable Read, and Serializable — ordered from the most permissive and fastest to the most restrictive and safest. Each step up the ladder rules out additional concurrency anomalies, and each step typically costs something in throughput, locking, or transaction retries.

This matters in COP4708 because isolation is a design decision, not just a runtime setting. The anomalies you studied earlier in this module — dirty reads, non-repeatable reads, and phantom reads — map directly onto the levels: a level is essentially a promise about which of those anomalies cannot happen. Knowing that mapping lets you justify a setting for a reporting query, a checkout flow, or an inventory decrement, instead of accepting whatever the database defaults to.

As you watch the videos below, keep three questions in mind. First, which anomaly does each level permit and which does it forbid? Second, how does the specific database engine implement the level — through locks, through multiversion snapshots, or through conflict detection and retries? Third, what does the engine's documentation actually guarantee, since real systems sometimes behave more strictly or differently than the standard's minimum requirements. Note also that vendors differ: a level name does not guarantee identical behavior across PostgreSQL, CockroachDB, MySQL, or SQL Server.

Concurrency Control Strategies and Best Practices

Introduction

When many users hit the same database at the same time, the system needs a strategy for deciding what happens when two transactions want the same row. The three broad families of answers are pessimistic concurrency control (lock the data first and make others wait), optimistic concurrency control (let transactions proceed and check for conflicts at commit time, usually with a version number or timestamp), and multiversion concurrency control (keep multiple versions of each row so readers never block writers and writers never block readers). Most modern systems, including PostgreSQL, combine these ideas rather than using just one.

This matters in COP4708 because isolation levels, locking behavior, and deadlocks are not abstract theory — they are the direct consequence of which strategy your database engine uses and how you write your transactions. Choosing the wrong approach for your workload shows up as lost updates and corrupted data on one extreme, or as lock contention, timeouts, and sluggish throughput on the other. The practical goal is consistency that does not cost you performance, which means matching the strategy to the read/write mix and conflict rate of your application.

As you watch, keep a comparison table in mind: for each strategy, note who waits, when the conflict is detected, what happens when a conflict occurs (block, retry, or abort), and what the cost is (lock overhead, retry overhead, or version storage and cleanup). Also watch for the classic motivating example — two users buying the last item — and ask yourself which strategy you would choose if conflicts are rare versus frequent, and how you would monitor the result in production.
