Introduction

When many users read and write the same data at the same time, a database needs a way to decide who may touch what, and when. Locking is the most common mechanism for making that decision. A shared (read) lock lets several transactions read the same item concurrently, while an exclusive (write) lock gives one transaction sole access so that no one else reads or modifies the item mid-change. Intent locks sit above these at coarser levels of the data hierarchy, signaling that a transaction holds or plans to hold locks further down so the engine can detect conflicts without inspecting every row.

Lock granularity is the second half of the picture: a lock can cover a single row, a page, a partition, or an entire table. Fine granularity allows more concurrency but costs memory and bookkeeping, so engines perform lock escalation, converting many fine-grained locks into one coarse lock once a threshold is crossed. That conversion protects the lock manager but can suddenly block other users. This is the central trade-off of the topic and of this course module: more locking means stronger data protection and fewer anomalies, while less locking means better throughput and more risk.

As you watch the videos below, keep three questions in mind. First, which lock modes are compatible with which others, and why does that compatibility matrix matter? Second, at what level of the data hierarchy is each lock being taken? Third, what happens when locks collide — blocking, waiting, or deadlock — and what does the database do about it? Connect what you see to the isolation levels and concurrency anomalies covered elsewhere in this module, since isolation levels are largely implemented through locking behavior.
