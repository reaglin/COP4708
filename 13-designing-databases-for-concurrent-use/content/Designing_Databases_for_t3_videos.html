Introduction

When only one person uses a database at a time, correctness is easy. Real systems, though, run many transactions at once, and the database interleaves their reads and writes to keep throughput high. That interleaving is where trouble starts: if two transactions touch the same rows at the wrong moments, one of them can read data that was never committed, see different values on repeated reads, or silently overwrite another user's work.

This topic gives names to those failures so you can recognize them precisely. A dirty read happens when a transaction reads uncommitted data that is later rolled back. A non-repeatable read occurs when a transaction re-reads a row and finds it changed. A phantom read occurs when a repeated query returns a different set of rows because another transaction inserted or deleted data matching the search condition. A lost update occurs when two transactions read the same value, each computes a new value, and the second write erases the first. Each of these is a specific pattern of interleaved operations, not a vague "bug" — and each one chips away at data integrity in ways that are hard to detect after the fact.

As you watch, focus on the timelines. Try to redraw each scenario as two columns, Transaction A and Transaction B, with the read, write, commit, and rollback steps in order, and mark the exact moment the anomaly becomes possible. Being able to produce that diagram from memory is the skill you will need later in the module when you choose isolation levels and concurrency control strategies.
