Introduction

When many users read and write the same data at the same time, a database must decide how much one transaction is allowed to see of another transaction's in-progress work. Transaction isolation levels are the standard knobs for that decision. The SQL standard defines four of them — Read Uncommitted, Read Committed, Repeatable Read, and Serializable — ordered from the most permissive and fastest to the most restrictive and safest. Each step up the ladder rules out additional concurrency anomalies, and each step typically costs something in throughput, locking, or transaction retries.

This matters in COP4708 because isolation is a design decision, not just a runtime setting. The anomalies you studied earlier in this module — dirty reads, non-repeatable reads, and phantom reads — map directly onto the levels: a level is essentially a promise about which of those anomalies cannot happen. Knowing that mapping lets you justify a setting for a reporting query, a checkout flow, or an inventory decrement, instead of accepting whatever the database defaults to.

As you watch the videos below, keep three questions in mind. First, which anomaly does each level permit and which does it forbid? Second, how does the specific database engine implement the level — through locks, through multiversion snapshots, or through conflict detection and retries? Third, what does the engine's documentation actually guarantee, since real systems sometimes behave more strictly or differently than the standard's minimum requirements. Note also that vendors differ: a level name does not guarantee identical behavior across PostgreSQL, CockroachDB, MySQL, or SQL Server.
